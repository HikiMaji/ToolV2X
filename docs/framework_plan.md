## 判断

这个项目需要先形成从因果输入、真实 P/F 能力、消息接收、驾驶任务输出到统一评价的完整实验链条，再判断工具价值和选择机制。模块测试应随搭建进行；判断研究方向的实验，应在真实模块和强固定基线齐备后进行。

此前恒速/岭回归试跑只能检查数据和接口。其负结果不能作为停止 ToolV2X 或要求先通过一个自建小模型门槛的依据。P_state 的定义也只是那次试跑的候选，不约束新框架。

“完整”指这些环节能共同完成同一个任务，不要求现在搭服务平台、多车多工具管理系统或确定最终 Agent 架构。离线任务链完整也不等于完成闭环驾驶实验。

## 原框架复用的具体边界

1. 当前优先复用 CMP 的 `MotionTransformer` 预测模块。它在本项目中可以提供 P/F 内部的预测能力，不强制继承 CMP 的完整协同感知—预测融合流程。
2. 原 MTR 使用邻车历史上下文。信息等价 P_history 必须覆盖 F 实际读取的上下文，不能只传目标自身历史却宣称输入相同。P 返回当前状态、轨迹历史或按查询返回局部结果，以及接收端缓存如何形成，需要在整条链中共同设计；不能把 P 输入送到原模型未训练过的模式来制造 F 优势。
3. CMP 原聚合器依赖 GT 对齐身份、BEV 等输入且不输出 peer-only 目标。它可作为原框架对照，但用于可部署 ToolV2X 时必须明确修改关联、输入和新增目标处理，不能补零后称完整复现。
4. 规划端优先核查 V2V-GoT 原任务/模型入口的复用方案。它原本融合多车特征，QA 生成又包含 GT 未来信息；不能仅将节点改名为工具就当作独立远端服务。是否能因果地接收结构化 P/F、需要哪些适配与训练，仍待完成审查，不在这里静默决定拼接两个模型。
5. 原模型的坐标、时间编码和目标选择一旦改变，会发生输入分布变化。单次前向成功仅证明接入，不证明现存权重在新协议下有可靠能力；后续应在原网络上做必要训练和一致的任务验证。

## 接下来按什么顺序推进

先确定任务输出端和统一的原模型数据流，补齐 P/F 调用、接收与固定对照。搭建过程中继续做字段、时序、权重和数值检查；链条可以完成相同任务以后，再进行能力、成本和选择机制实验。更换预测器、感知方式或规划端时保持配对控制，不能用不同系统的偶然差异解释工具收益。

这条顺序允许先搭框架而暂不确定最终机制：先让固定策略完整运行，再让数据帮助选择合理的 ToolV2X 机制。
