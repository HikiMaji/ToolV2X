## 一、最需要先修：`one_shot` 会把完整本地证据塞进请求，可能直接退化成 Ego

**位置：`src/planning/method_controls.py::episode_bundle()`；`src/planning/method_episode.py` 的发送前预检。**

当前单轮请求的摘要这样构造：

```python
summary = {
    key: copy.deepcopy(state[key])
    for key in ('ego_motion', 'local_evidence', 'current_plan')
}
```

这里的 `local_evidence` 是完整本地字段，包括全部本地目标的预测与元数据，**不是按上行预算筛选过的摘要，也不是已经进入驾驶器的局部 Z**。构造函数没有提供独立的摘要裁剪或压缩规则。

随后，执行器在请求过大时直接替换成 STOP：

```python
if size > spec['max_request_bytes']:
    decision = dict(
        tool='STOP',
        mode=None,
        reason='request_byte_limit'
    )
```

因此，这条路径不会一定报错，而可能保存一个 `completed`、实际零查询的 episode。

### 本轮复现

使用默认 `ExecutionSpec`、合法合成状态，以及测试中使用的三个候选方案配置，执行当前 `episode_bundle()` 函数体：

| 本地目标与预测 | 单轮请求大小 | 同状态的普通首轮请求 | 4096 B 上行上限下 |
|---|---:|---:|---|
| 1 个目标，简单数值 | 3010 B | 614 B | 可以通过长度检查 |
| **2 个目标，简单数值** | **4203 B** | **614 B** | **单轮请求被转成 STOP** |
| 2 个目标，非重复全精度预测 | 6309 B | 614 B | 被转成 STOP |
| 20 个目标，非重复全精度预测 | 46564 B | 614 B | 被转成 STOP |

对“两目标、简单数值”继续执行原决策／预检片段，得到：

```text
status = completed
stop_reason = request_byte_limit
requests = []
```

**这不是实际数据的失败率，但已经足以证明该执行问题存在。**

现有 T6 集成测试继承的配置是 **30000 B 请求、30000 B 响应、100000 B 总预算、12000 token 上下文**，因此它们通过，并不能排除默认配置下的问题。

### 为什么重要

这里没有虚构工具调用，也没有越过预算；问题是：

> 对照名字叫 `one_shot`，实际却可能因为一个未经预算化的摘要构造方式，大量变成 Ego-only。

以后即使两轮方法胜过它，也不能排除只是单轮根本没有成功发出请求。

### 建议的最小修改

给单轮增加**明确、可配置、请求前确定的摘要构造规则**。在总预算内允许使用运动状态、初始方案、候选方案及经过选择的本地字段，而不是强制发送全部本地预测。

不要走两个极端：既不能为了省字节把有用摘要全部剥掉，故意削弱单轮；也不能仅给单轮放大总预算。应保留合理的摘要配置，并记录“策略原选择”和“最终实际执行动作”。

**这项建议在 T7 正式分支制作前处理。**

## 二、成本口径有错误：`control_seconds` 把保存快照的耗时算进去了

**位置：`src/planning/method_episode.py` 的控制决策计时；`src/evaluation/framework.py::_method_cost()`。**

当前顺序是：

```text
control_begin
    ↓
构造策略状态、调用策略
    ↓
emit('decision')
    ↓
构造请求、检查预算
    ↓
记录 control_seconds
```

而 `emit()` 会同步执行：

```python
on_progress(copy.deepcopy(episode))
```

也就是说，**decision 快照的复制与持久化回调，处在控制计时区间内**。

### 本轮复现

我没有真实等待或改变模型计算，而是使用注入时钟，仅改变保存回调的耗时：

| 注入的 decision 保存耗时 | 记录的 `control_seconds` |
|---:|---:|
| 0 秒 | 0 秒 |
| **7 秒** | **7 秒** |

策略和请求逻辑完全相同。

T5 又把 `control_seconds` 加进 `total_compute_seconds`，但声明的计时范围明确排除 persistence I/O。因此，**实现与成本口径不一致**。

### 后果

如果以后价值标签扣除计算时间，磁盘性能、快照大小和归档策略就会影响“这个请求值不值得执行”。尤其后续阶段的 episode 更大，保存耗时可能随交互阶段变化，不能把它误认为请求机制本身的计算成本。

### 最小修复

保留原子保存和失败留痕，但把控制计算计时拆成回调前、回调后两个区间；或者单独记录 `persistence_seconds`，从当前声明的计算效用中排除。

**不要通过关闭保存、减少失败记录来修这个问题。**

## 三、`available_actions` 还不是“预算下真正可执行的动作”

**位置：`src/planning/method_episode.py` 的动作列表构造与选后预算检查。**

现在可选动作主要根据两个条件生成：剩余调用次数，以及旧／新方案是否不同。请求序列化长度和剩余字节预算，是策略选完之后才检查。

因此，存在这样的路径：

```text
available_actions 包含 F_change
    ↓
策略选择 F_change
    ↓
绑定完整参数后发现请求超额
    ↓
直接 STOP
```

但此时 `F_current` 可能仍然可以支付。

### 本轮复现

在一个合法的低上行预算配置中：

```text
max_request_bytes = 640

available_actions:
STOP / P_current / F_current / P_change / F_change
```

实际结果：

| 策略选择 | 预检结果 |
|---|---|
| `F_change` | 转成 `STOP: request_byte_limit` |
| `F_current` | 请求为 **613 B**，可以通过该预检 |

这里的 `F_current` 结果只表示可以通过预检，**本轮没有继续执行服务调用**。

### 为什么值得现在修

当前诊断策略遇到它，主要表现为提前停止；到了 T7/T8，它会进一步影响动作标签和部署策略：

> “某动作不可执行”与“某动作执行后没有收益”不是同一种监督情况。

也不能把“选了一个不可支付动作，执行器被迫 STOP”混同于价值网络主动判断停止最优。

### 最小修复

执行器在调用策略前，为候选动作绑定已知的轨迹、manifest 和配置，计算真实请求长度，再按**公开的响应上限**过滤不可支付动作。

这些信息本来就属于本车已知内容，不需要提前读取 peer。发送前的最终预算检查仍然保留。

**这属于可行动作 mask 的补齐，不需要修改价值网络结构。**

## 四、需要明确的对照问题：单轮与两轮的下行额度目前不等价

**这项是实验口径问题，不是数组越界或服务计费错误。**

当前单轮构造要求：

\[
\sum_i \text{primitive response cap}_i
+\text{wrapper reserve}
\leq \text{一次 max\_response\_bytes}.
\]

普通两轮则每次各有一份 `max_response_bytes`，再受 episode 总预算约束。

使用默认响应上限 **8192 B**、测试中的 wrapper 预留 **2048 B** 时：

| 执行方式 | 响应容量安排 |
|---|---|
| 单轮、两个内部原语 | **3072 B + 3072 B**，另留 wrapper |
| 普通两轮 | 每轮最多 **8192 B**，合计下行上界 **16384 B**，仍须满足总预算 |

因此，“两边配置里都写了相同 `ExecutionSpec`”并不意味着它们拥有相同的聚合下行能力。

### 怎么解释才准确

**相同每包上限**可以作为一个合理的研究条件，但该条件下的差异，不能自动全部归因为驾驶反馈。两轮同时获得了发送两份较大响应的机会。

若要验证“真实中间反馈是否不可被单轮替代”，还应有**相同总双向字节预算、相同原语次数**的对照，允许单轮在剩余额度内组织一次合法聚合返回。

建议明确区分：

```text
原语输出容量
单次外层响应容量
episode 总双向预算
```

不一定现在实现复杂的动态装包算法，但至少不能用当前固定对半分配、较小聚合上限的单轮配置，直接代表“strong one-shot 已被公平检验”。

## 五、T3–T6 中已经做对的部分

上述问题不意味着这一批整体实现失败。相比 T1/T2，现在确实补上了几个关键环节。

**T3 的 E／派生／Z 分离是真实实现。**远端字段保存在 `acquired_fields`，本地预测单独保存父引用和输入上下文，实际入模字段与丢弃项另外记录。完整 P 证明考虑了原窗口顺序、dtype 和 predictor binding，而不是仅凭相同模型名字归并预测。

**T4 的交替驾驶调用也已经存在。**初始方案、工具返回、更新 ledger、再次调用同一 driver、用实际新旧方案形成后续请求，都能在代码路径中追踪到；不是人为修改一条轨迹冒充 GoT 修订。

**T6 单轮返回的接收边界处理正确。**接收端从实际外层 wire 重建内部响应，而不是直接使用返回对象中未经传输的 `primitive_responses` sidecar。continuation 的接口也限定为外发内容、真实首返回和合法动作列表，没有直接传入 ego driver 或窗口 loader。

**上轮 T1/T2 的四项边界问题，当前源码都有对应修复。**包括数值列表中的 bool、请求 JSON-native 类型、预测返回的 NumPy 契约，以及有效历史尺寸检查。但本轮没有完整复跑那批修复测试，不能把源码核对说成全部独立验收。

在已读调用链中，**我没有确认新的查询前 peer 数据读取旁路或 GT 进入在线决策的问题**。这是一项有限范围的代码判断，不是完整环境运行证明。
