**可以继续保留 ToolV2X，但不应该为了保住名字，把系统强行改造成“看起来像 Agent”的样子。你需要加强的不是工具调用的外观，而是“本车向邻车委托什么任务、如何使用返回结果、为什么下一次委托因此改变”。**

你的直觉有一部分是对的：**目前已经具备工具服务，但“工具使用机制”还不够突出。**你上一条 v0.1 正在补这个缺口。不过，“更像 Tool”与“更有论文贡献”是两件事，必须分开判断。

## 一、现在到底哪里“不够 Tool”？

我重新核对了能够读取的公开版本 `494e04d`。其中 `VehicleTools.query()` 是真实的 P/F 服务：查询后才读取邻车窗口，P 返回历史，F 执行或复用预测，再按 ROI 返回；`episode.py` 的规则会读取真实响应，但主要依据速度和目标关联情况决定下一步，没有把 GoT 的方案修订作为请求参数。

所以我的诊断是：

| 层次 | 当前判断 | 真正缺少什么 |
|---|---|---|
| **可调用的外部能力** | 已经有 | 不是必须再增加网络或工具数量 |
| **任务条件化的工具使用** | 已有初步规则，v0.1 尚需实现 | 驾驶任务如何决定具体请求，返回如何改变后续任务 |
| **以工具使用为核心的论文贡献** | 尚未建立 | 相对强通信／任务请求基线的可归因收益 |

目前最容易给人“只是通信策略”的感觉，是因为主问题还比较接近：

> **这次拿 P 报文，还是拿 F 报文？**

而你真正想研究的应该是：

> **为了完成当前驾驶任务，我应该委托邻车检索或计算什么？收到结果后，下一项需要解决的问题是什么？**

后者不一定要用自然语言表达，但必须影响实际执行。

---

## 二、“Tool”不等于新网络、自然语言或 LLM 直接写函数名

这一点需要明确，否则很容易往错误方向加功能。

Toolformer 研究的就是选择 API、调用时机、参数以及如何利用结果，其中包括检索、问答等能力；ReAct 也使用简单的 Wikipedia API 获取信息。它们并没有把“每个工具必须是新训练的神经网络”作为工具成立的条件。

更直接地，DriveAgent-R1 的工具包含历史视图检索、ROI 裁剪、深度估计和三维检测。**读取历史或裁剪既有输入，同样可以是工具，不需要每次调用都创造一种新能力。**

因此，你的：

- **P：在邻车私有历史中检索与任务有关的跟踪证据；**
- **F：在邻车私有上下文上执行运动预测；**

可以构成合理的工具集合。只有两个工具也不是问题。

但也不能反过来说：“包成 API 就构成论文创新”。CoDriving 已经用驾驶请求指导协作信息选择，Select2Drive 也利用规划相关区域组织通信。因此，**任务导向通信和工具化委托存在重叠，不是两个互斥领域。**

**你不需要证明 ToolV2X“完全不是通信”。它当然需要通信。你需要证明：在通信之上，任务级调用与反馈组织带来了额外价值。**

## 三、我建议加强三个实质特性，而不是增加一堆工具

### 1. 从“选择报文类型”加强为“调用带任务参数的能力”

这是第一优先级，也是 v0.1 最值得保留的部分。

目前接口大致是：

```text
query(P 或 F, ROI)
```

建议改成有明确执行语义的请求：

```text
P.retrieve(task_spec)
F.forecast(task_spec)
```

这里换名字没有意义，关键是 `task_spec` **真的决定提供方做什么**。

首版可以直接采用你已有的 current/change，不需要扩大到十几个任务：

| 请求内容 | P 的执行 | F 的执行 |
|---|---|---|
| 当前方案 `current` | 根据当前状态、合法历史趋势和请求轨迹，检索相关历史 | 基于完整邻车上下文预测，再按与请求轨迹的时间关系选择目标 |
| 方案变化 `change` | 检索旧／新方案之间相关性发生变化的历史证据 | 根据旧／新方案与预测的时序关系，选择值得返回的预测 |

请求至少包含实际方案、时间与坐标定义、任务模式，以及固定输出约束。**不能只是附上一条轨迹，但提供方仍然忽略它、返回同一份固定 ROI 报文。**

可以用一个很直接的执行测试检验：

> 固定邻车输入，只改变合法任务参数，提供方是否按规格改变检索／排序／返回结果？

不是要求每次参数变化都必须返回不同对象，而是要求结果变化符合执行器定义。

同时保留两条边界：

**P 不得偷偷调用 MTR 后再把结果叫作观测检索；F 可以用 ego 方案筛选预测，但不能因此宣称 MTR 已经预测了他车对 ego 方案的反应。**后者需要真正的交互条件化预测模型，当前方案并没有这一能力。

这一步让请求成为**可执行任务**，而不只是消息标签。

### 2. 从“结果影响是否再调用”加强为“结果参与构造下一次请求”

这是我认为最值得加强的 Tool 特性。

简单的反馈是：

```text
P 返回了目标 → 再调用 F
```

更完整的反馈是：

```text
收到真实结果
→ 更新已知事实
→ 同一 GoT 生成修订方案
→ 根据修订后的任务需求构造下一次请求
```

可以写成：

\[
q_k=(u_k,\theta_k),\qquad
r_k=T_{u_k}(X_{\rm peer}^{\leq t};\theta_k),
\]

\[
\theta_{k+1}
=
g\!\left(\tau_k,\tau_{k+1},E_{k+1},B_{k+1}\right).
\]

其中 \(u_k\) 是 P 或 F，\(\theta_k\) 是请求参数。关键不只是下一步的工具名改变，**请求所针对的问题也能因为真实结果而改变**。

一个假设例子是：

> Ego 先形成 \(\tau_0\)，直接请求与它相关的 F。邻车返回目标预测后，GoT 产生减速方案 \(\tau_1\)。减速改变了相遇时刻，第二次请求转而获取与这一变化有关的 P 历史，或者判断没有进一步价值而停止。

这里可以 F→P，也可以 P→F、P→P、F→F，**但序列必须有实际信息增量或合理计算价值，不能为了展示组合而强制运行。**

特别是：已经获得完整 P，并且已经完成同模型、同上下文的本地重算时，再获取完全相同的 F，不应被解释成能力互补。

**你 v0.1 的“真实修订＋current/change”已经朝这个方向走。优先把它实现，比增加第三、第四种工具更有意义。**

### 3. 从“收到 JSON”加强为“可验证、可引用、可继续使用的结果”

工具返回最好不仅是一些数值，还需要明确这些数值是什么、可以怎样继续使用。

我建议保留或补齐三类信息：

**结果身份。**提供方、scene、时间、源内目标句柄、请求 ID。目标句柄必须来自真实返回，不能由本车凭空指定邻车尚未公开的目标。

**结果边界。**P 返回的是跟踪历史还是检测观测，F 使用了什么上下文，历史是否不足，哪些部分是回退，是否截断，结果是否复用缓存。不要让一个 `success` 掩盖这些差异。

**已获字段与实际入模字段。**同一个目标的历史、局部上下文预测和完整上下文预测不能混为一项；已经收到但被驾驶器截断的内容，也不能算作“驾驶器已经理解”。

这样下一次请求可以合法地表达：

> 已经有这些目标的预测，但缺少原始历史；或者已经有部分字段，不要重复返回相同内容。

这会形成真正的**返回结果到下一请求参数的引用关系**。

不过，我不建议首版立刻把“目标句柄寻址”也加入学习动作空间。先保持 current/change 的有限动作，把句柄和字段清单作为执行器支持；后续单独验证精确寻址，避免把“多了一种寻址能力”和“反馈机制更好”混在一起。

**这些契约本身是工程基础，不是独立创新，但能防止工具机制变成不可核对的故事。**

## 四、要不要让 GoT 自己生成工具调用，才算“足够 Tool”？

**不必现在这样做，但论文表述要匹配真实实现。**

### 我更推荐的首版

```text
GoT：产生驾驶方案与任务表征
        ↓
请求策略：选择能力、任务模板和停止
        ↓
确定性执行器：绑定合法参数、检查预算、调用邻车
        ↓
真实返回：更新证据
        ↓
GoT：修订驾驶方案
```

这是一种**工具增强的驾驶系统**。请求策略可以是小型网络，也可以利用 GoT 的表征；并不要求 GoT 自回归生成整段 JSON。

这样能把“驾驶能力”和“调用决策”分开研究，也与 v0.1 只增加一个本车价值模块的收敛方向一致。

但若实际是外部策略选择请求，就不宜写成：

> “驾驶大模型自主学会了工具规划与函数调用。”

更准确的是：

> “驾驶任务条件化的请求策略，组织远端能力调用与重规划反馈。”

### 什么时候再考虑模型原生工具调用？

当你确实要研究：**语言模型的表征或生成式任务分解，是否比结构化策略更有优势**，再让模型输出受约束的调用动作。

届时需要与同信息、同监督、同能力接口的小策略比较，而不是默认“LLM 自己写调用”就更高级。ReAct、DriveAgent-R1 已经研究了模型生成调用并利用返回继续推理，所以仅把调用入口迁到 GoT 内部，也不会自动产生新贡献。

**现在不建议为“更 Tool”而增加自然语言思维链、另一套大模型或联合 RL。**这些会改变研究问题，却不一定解决当前最重要的任务请求与反馈归因。

## 五、哪些东西不值得为了名字去加？

我尤其不建议为了凑工具数量，立刻加入 `RiskTool`、`SafetyTool`、`CriticTool`、地图查询、RSU 或意图 I。

原因不是这些能力永远没用，而是每一种都需要回答：

> 它有独立的信息或计算来源吗？现有 P/F 无法合理提供的增量是什么？它的输出是否可靠，成本怎么计算？

比如把现有轨迹间距函数包成 `SafetyTool`，并不会自动获得安全验证能力；把 MTR 分数转换成一段“风险解释”，也不会得到校准碰撞概率。

同样，不应刻意禁止本车在完整 P 上重算，只为制造“必须调用 F”；也不应要求每个场景都调用两次。**会停止、能避免冗余调用，本来就应该是你要研究的能力。**

模型已计算结果的缓存复用也不使它“不像 Tool”。关键是缓存来源、有效时间和费用透明，不能给某个方法免费提供其他方法未获得的信息。当前服务已经区分了 F 缓存命中与新增模型计算，后续任务请求可以沿用这一边界。

## 六、怎么证明加强的是工具机制，而不是包装？

我会用下面四项实验作为核心验收，而不是用“调用 JSON 合法率”当主要成绩。

| 实验 | 怎样比较 | 能支撑的结论 |
|---|---|---|
| **任务参数是否有价值** | 固定 ROI 请求 vs current/change；共享接收器、能力与合理预算 | 收益是否来自请求内容，而不仅是有无通信 |
| **反馈是否有价值** | 固定相同首轮请求与返回，第二轮分别使用初始方案或真实修订方案 | 真实驾驶反馈是否改善下一次请求 |
| **交互是否可被单轮替代** | 两轮请求 vs 允许条件执行、合法摘要与 bundle 的强单轮委托 | 是否确实需要往返反馈 |
| **收益是否只是额外推理** | 新证据后的修订 vs 相同证据下的等量生成／迭代 | 信息获取是否有独立价值 |

这些都需要实际轨迹质量、失败、恶化比例和成本，而不是只观察“轨迹变了”。

特别要注意：**如果最多两次请求需要三次 GoT，而固定方法只需要一次，那么多出的驾驶计算就是方法代价的一部分。**不能先把它省略，再说 ToolV2X 更有效率。

论文真正有说服力的证据应该是：

> 在同等总资源约束下，任务化请求与真实反馈，获取了更有用的内容，并改善最终驾驶输出；这种收益不能被更简单的单轮委托或额外推理解释。

而不是：

> 系统现在会输出 `tool_call` 了。

## 七、到底要不要坚持 ToolV2X？我的明确建议

**研究主线继续保留，项目名暂时保留；不要把最终论文贡献绑在“Tool”这个单词上。**

我建议你对不同结果保持如下区分：

**如果任务请求、能力选择和返回后再委托确实产生了收益，**ToolV2X 很贴切。可以定位为：

> **ToolV2X：面向驾驶任务的远端能力调用与重规划反馈。**

**如果最终主要收益来自请求区域或消息选择，反馈与能力组合没有额外价值，**仍然可以有合理的任务导向协作方法，但应按实证结果收紧论文定位，不必硬讲复杂 Agent。

**如果只是把固定 P/F 数据流包装成 API，**工具服务在工程上成立，论文机制却仍然不足。改名不会解决这个问题，多加几个工具也不会。

因此，下一步我只建议增加一条完整链，而不是再扩展整个系统：

> **合法任务参数 → 邻车执行 → 带身份和能力边界的真实返回 → 同一 GoT 修订 → 结果参与下一次请求或停止。**

先在冻结底座下把这条链和四项对照做出来。**让 ToolV2X 名副其实的，是“委托任务与组合结果”的可验证价值，不是工具数量、自然语言程度，也不是必须由 LLM 亲自写出函数名。**
