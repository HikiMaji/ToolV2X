## 二、发现的具体问题

### 1. P2：数值数组中的混合布尔值可以绕过类型校验

**位置：`src/tools/task_spec.py:53–58`，以及使用 `_array()` 的请求和响应校验路径。**

现在的检查是：

```python
array = np.asarray(value)
if array.dtype.kind not in 'fi':
    raise ValueError(...)
```

问题在于：**先交给 NumPy 转换，再检查 dtype，会丢失原始元素的布尔类型。**例如 `[True, 0.0]` 会变成浮点数组，因此通过检查。请求时间轴、轨迹、历史和预测数据都复用了这个入口。

我实际验证了：

| 篡改方式 | 当前行为 |
|---|---|
| 把 `times[1]` 的 `1.0` 改成 `True` | 请求校验和服务执行均通过 |
| 把一个 `tau_new` 坐标改成 `True` | 服务执行通过 |
| 把 F 响应的一个预测坐标改成 `True` | `decode_task_response()` 通过 |
| 把历史／anchor 中的零坐标改成 `False` | 解码通过 |

**可观察后果：**错误 JSON 类型被静默解释为 0 或 1，而不是在协议边界拒绝。它没有证明当前正常模型输出已经出错，但与“严格数值字段”的接口目标不一致。

**最小修复：**对原始列表／元组中的数值叶子先做类型检查，明确拒绝 `bool`，再进行 NumPy 转换；已有 NumPy 布尔数组也拒绝。不要用 `float(True)` 将错误输入“修正”为合法数值。

现有测试检查了整数参数中的 `True`、非布尔 validity mask 等情况，但没有覆盖**混合数值数组里的布尔元素**。

### 2. P2，条件性触发：预测结果的校验、缓存与装包接受的类型不一致

**位置：`task_spec.py:242–256`；`vehicle.py:140–148`；`prediction_objects()`。**

`rank_targets()` 会把预测值临时转成 NumPy 数组进行校验，因此可以接受 list-backed 的合法预测。可是转换后的值没有交给下游：

```python
ranked = rank_targets(w, request, forecast)
self._task_forecast = copy.deepcopy(forecast)
...
prediction_objects(w, forecast)
```

后面的 `prediction_objects()` 又假定 `means` 支持 NumPy 多维索引、`scores` 支持 `.tolist()`。因此，**排序器接受的表示，不一定是装包器能够消费的表示，而且它已经进入缓存。**

我用仓库的 `fixture_prediction`，仅将其输出数组转换成列表，保持数值和语义不变，得到：

```text
第一次 F：
rank_targets 校验通过
→ 原返回对象写入缓存
→ 装包 TypeError

第二次 F：
命中该缓存
→ 再次装包 TypeError
```

两次错误都是：

```text
list indices must be integers or slices, not tuple
```

第二次记录为 `cache_hit=True`、`model_seconds=0`，两次调用额度被耗尽。

**边界要说清楚：目前原 CMP 正常返回 NumPy 数组，本轮没有观察到真实 CMP 因此失败。**这是新接口面对包装器或 array-like 返回值时的契约不一致，不是“当前 MTR 全部不能用”。

**最小修复二选一：**在 v2 边界统一规范化预测结果，再校验、缓存和装包；或者明确只支持 NumPy 数组，在缓存写入前拒绝其他表示。无论选哪种，都不要为此改变旧 v1 helper 的既有行为。

### 3. P3：tuple 轨迹通过预检，却在读取邻车数据后才因请求回显失败

**位置：`task_spec.py:129–149`；`vehicle.py` 的 `query_task()` 和 `decode_task_response()`。**

当前数值检查和 JSON 可序列化检查都接受：

```python
tau_new = [(2.0, 0.0)] * 6
```

但序列化后，tuple 会成为 JSON 数组；解码回来是 list。随后将解码后的请求与原始 Python 请求比较，会因为 list／tuple 不同而失败。

实测结果是：

```text
validate_task_request：通过
query_task：已经读取窗口，并记录一次执行和请求字节
最终：response request/coverage contract mismatch
```

**这不是查询前信息泄漏，但属于本可以在预检阶段解决的输入问题，实际却消耗了一次执行机会。**

建议明确选择：仅支持 JSON-native list，就在私有读取前拒绝 tuple；支持常见容器，就在入口无损规范化，并让校验、序列化、回显和返回 request 使用同一规范表示。这个规范化不能掩盖第一项的布尔类型错误。

当前 GoT 输出的正常列表轨迹不触发它，因此优先级低于前两项。

### 4. P3 加固项：有效历史状态中的非正尺寸没有被拒绝

**位置：`task_spec.py:176–196`；`vehicle.py:474–483`；依赖的 `history_packet()`。**

当前主要检查最后一个状态的框尺寸为正，过去状态则检查形状和有限性。把一个 `valid=True` 的过去状态的 length 改成 `-4.0`，P 服务和响应解码仍然接受。

这项需要准确归类：**它是沿用旧校验的防御缺口，不是本次提交造成的 v1 回归；我也没有核实真实缓存中存在负尺寸。**

后续 P 本地重算会消费有效历史，因此建议增加：

```text
仅对 valid=True 的历史状态：
length、width、height 必须为正。
```

不要连缺失历史的零占位也拒绝。对应测试应同时保留“合法缺历史零占位”和“非法有效历史尺寸”两个分支。

## 三、此前最重要的约束，这次确实落实了

上面的边界问题之外，**本批最关键的设计并没有实现偏**。

### ExecutionSpec 与协议语义已经分开

参数集中在 `ExecutionSpec`，请求携带完整配置，同一已开始的 episode 不允许换配置重置预算。没有继续把预算、sigma 和车辆尺寸散落进业务代码。这个要求已经满足。

### 回执不是“客户端说有就有”

`validate_task_request()` 使用的是服务实例自己的 `_task_receipts`；只有实际返回到最终报文里的字段才登记，未发送候选和旧 references 不会被签成新的拥有证明。相关检查发生在窗口读取前。

原测试中的伪造、跨场景／时间／上下文、其他实例回执、已计算但未返回字段等负例，本轮均通过。

### P/F 执行边界正确

P 使用最新两个有效 tracking states 和真实时间间隔做检索代理，不调用 MTR；F 先使用完整提供方窗口，再做任务排序和装包。预测器收到独立副本，修改固定窗口的行为会被拒绝；v1 也不能免费预热 v2 缓存。

完整 P 后再请求 F 仍然合法，**没有在 T2 偷偷实现“本地派生 F 已经等价拥有，所以屏蔽远端 F”**。这一层次划分保持住了。

### current/change 不是只改变请求名字

实际排序使用了请求轨迹、包围圆间距、sigma，以及对应的 current／change 得分。change 确实是**同一时刻、同一模式先作差，再聚合**。

我另用独立的标量循环计算关系分数，在 240 组不同目标、历史、模式和参数条件下，与代码排序结果一致。这个结果支持公式实现正确，**不代表该启发式已经改善驾驶任务**。

### 字节与失败账本处理较扎实

实际 cap 检查覆盖完整 UTF-8 报文，而不仅是 payload；原子 bundle、请求回显、非 ASCII、空响应和 JSON `true/false` 长度差均有对应测试。已开始执行后失败，调用额度与请求成本也会留下；模型完成量不确定时使用 `None`，没有假填 0。

这里的边界仍是**同机服务的执行契约和应用层字节**，不是实网时延、断电持久化或密码学认证。

### v1 兼容不是只靠“测试没报错”

我还核对了父提交 `4351096` 的原 `vehicle.py`：旧 `query` 与六个辅助函数的 AST 保持一致；固定计时器后，P 全量、F 窄 ROI、F 缓存、P 空 ROI、F 空 ROI 的连续调用，完整 request／wire／cost 均一致。

## 四、三处我不会误报成缺陷，但 T3 必须承接

**未附 manifest 时允许重传，不等于去重失效。**实施报告明确把 manifest 定义为“收到确认”：未确认的字段可以重传，身份不变、字节照计。这个选择合理，尤其“已发送”并不必然等于“已收到”。后续正常请求构造器应从 E 自动生成完整 manifest，且不能把重传记成新信息。

**`name/revision` 还不是内容指纹，但现在不需要因此重写 T1/T2。**本批去重依靠固定服务实例和已签发回执；跨实例、跨本地派生的完整同信息证明仍留给 T3。报告已经明确没有把相同版本字符串当作数值等价证明。

**按 response cap 保守预留预算，不是算错账。**它可能拒绝一个实际上能装下的小响应，但这是未知远端内容时的保守策略。只要对照共享该规则，就可以继续使用；后续不能把它称为已经优化过的通信效率。

另外，现有 T2 大部分服务测试使用了比默认值更宽的预算配置。因此，正式接入 T3 时，仍应对默认预算及预设预算档做**代表性报文容量检查**，不要把契约通过直接理解成“默认容量足够支持两次有效请求”。

## 五、现在应该怎么交给 Codex

**不需要再重写实施计划，也不需要扩展方法。**建议只做一次输入边界与缓存契约的小修复：

> 修复数值数组混合 bool 的校验；统一请求容器的接受／规范化规则；统一预测返回表示的校验、缓存与装包契约；补充有效历史尺寸检查。保持 current/change 公式、P/F 能力边界、回执语义、预算规则和旧 v1 行为不变。先运行新增反例、原 43 项和原环境的全部轻量回归，不启动模型训练或新方法实验。

完成这批修复后，**我支持继续 T3，不建议再围绕 API 包装、复杂 fingerprint 或新工具数量停留一轮。**

T3 接下来真正要解决的是：完整保存已购 E、区分本地派生、构造实际入模 Z，并确保这次任务检索选出的内容没有在驾驶输入阶段被错误丢弃或重复计入。当前审查入口也准确地把这些，以及 GoT 交替修订、价值网络和方法效果，列为未完成事项。

**总体上，这次更新是实质进展：ToolV2X 已经有了真正按任务参数执行的 P/F 服务。现在差的不是再证明“它像不像 Tool”，而是把这份服务稳妥接入 E/Z 和真实驾驶反馈链。**

但有两点需要收紧我上一轮建议的表达。
不必为了修复，扩大接口支持范围
对 list-backed predictor 和 tuple 请求，“明确不支持，并在正确的边界拒绝”也是合格修复。
你不需要让 Codex 为了把反例变绿，额外实现一个能兼容任意 Python 容器、任意预测包装器的通用转换层。最小方案可以是：
v2 请求只接收明确的 JSON-native 数据结构；v2 predictor 只接收／返回明确的 NumPy 数组结构；非法类型尽早拒绝。

真正的问题不是“不支持某个类型”，而是前面声称接受，后面才失败，甚至把它存成可复用缓存。
不要把所有响应失败都解释成“必须清空预测缓存”
需要修复的是：
不兼容或非法的预测结果不能进入可复用缓存。

不是：
“只要装包、预算或其他响应环节失败，就删除已经合法计算的 F。”

例如完整预测本身合法，但当前响应预算装不下某个 bundle，保留同刻合法缓存未必有问题。否则会人为增加重复计算，反而改变成本语义。当前报告也明确区分了完整预测、缓存命中和实际返回字段。
四、几件事不应再升级成阻塞问题
**不附 manifest 时允许重传，是明确的协议选择。**它不等于去重漏洞。实现报告把 manifest 定义成“收到确认”，没有确认时可以重传、字节照计、身份不变。T3 负责正常生成完整 manifest，并区分重传与新信息。
**当前回执注册表不是密码学认证系统，也不需要现在变成一个。**本批验证的是固定服务实例内，字段引用必须来自真实已返回记录。内容 fingerprint、跨实例持久化和本地派生等价证明已明确后置，不能因为这次复审又要求 T2 实现完整安全协议。
**按完整 response cap 保守预留预算，不是算错账。**它可能比实际所需预算保守，但实现和文档一致。后续对照共享这个规则即可；是否要优化它，应该成为独立、明确的工程调整。
同样，T3 的 E／derived／Z、真实 GoT 修订、强单轮和价值网络尚未完成，是当前批次边界，不是 T1/T2 没有完成承诺。
五、现在可以怎样推进
我建议保留 T1/T2 的总体实现，只做一次 v2 边界补丁，然后进入 T3。
这次补丁应限定为：数值类型检查、请求容器契约、预测返回契约与缓存写入条件、有效历史尺寸检查。不要改 current/change 公式，不要改 P/F 信息边界，不要改已确认的回执和预算语义，也不要为修复去动旧 v1 helper。
T3 的设计工作可以继续；在正式收集新机制分支之前，把这些边界修好，并在原环境重跑原 43 项、完整轻量套件和新增反例即可。没有必要因为这些边界问题再次暂停全部方法推进、重建缓存或增加模型训练。
