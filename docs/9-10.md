## 一、需要修复的实现问题

### 1. P1：主运行器没有真正使用配置的数据根目录

**位置：`src/planning/run_connection.py:73–74`。**

`prepare()` 仍然直接执行：

```python
features = load_ego_features('/root/autodl-tmp/V2V-GoT', 'train', g)
motion, motion_paths = load_ego_motion('/root/autodl-tmp/V2V-GoT', 'train', g)
```

这两处绕过了已经支持 `TOOLV2X_V2VGOT_ROOT` 的统一读取层。相比之下，`adaptation_data.py` 使用的是 `M.V2VGOT_ROOT`，因此主运行器和训练数据准备器可能读取不同的数据根目录。

**触发条件与后果：** 在新机器上按 README 设置数据根目录，准备好其余资源后运行 `run_connection.py`，它仍会访问旧路径。旧路径不存在时直接失败；旧路径恰好存在时，更危险的情况是继续读旧数据，而不是用户配置的数据。

现有可移植性测试只检查 `M.load_pose()` 是否服从环境变量，没有覆盖 `prepare()` 的实际调用，因此这个测试通过不能证明主入口已经可迁移。

**最小修复与验证：** 两处统一改用 `M.V2VGOT_ROOT`。新增入口级测试：配置临时数据目录，拦截 `load_ego_features()` 和 `load_ego_motion()`，断言实际传入的根目录正确，而不只是测试底层 helper。

### 2. P1：合法 Q8 回答可能突破 Q9 预算，并丢失该动作的生成记录

**位置：`v2vgot.py` 的 `fit_evidence()`、`_generate()`、`plan()`；`inputs.py:202` 的 `parse_q8()`。**

预算估计使用固定的短回答：

```text
The suggested speed setting is: very slow.
The suggested steering setting is: slightly right.
```

但 `parse_q8()` 只要求能够找到唯一且合法的 speed、steering 设置，并不拒绝回答前后的解释文字。实际 Q9 又会使用完整的 `q8_raw`，而不是这个预算原型。因此，**固定原型的长度不是解析器所接受的全部 Q8 回答的长度上界**。

**触发条件：** 所选 evidence 已接近预算上限，Q8 生成了合法设置，并额外附带解释文字。

**可观察后果：** `_generate()` 在 Q9 阶段抛出 `explicit token budget exceeded`。这个异常没有被 `plan()` 转成结构化失败结果，而 `infer()` 是在 `planner.plan()` 返回后才写 `plan.json`。因此不仅该动作没有正常的计划记录，已经生成的 Q8 也不会通过这里落盘，后续动作还会被中断；外层只留下运行级失败记录。

我用原预算函数和解析器做了一个**合成字符级 tokenizer 反例**：预算计算恰好为 4096，而一个仍可解析、长度不超过测试中 Q8 生成上限的回答，使实际需求变为 4125。这个数字不是原 SentencePiece tokenizer 的测量结果，但它验证了预算上界在逻辑上不成立。

**最小修复与验证：** 优先在 Q8 之前为允许生成的父回答留足预算，并在得到真实 Q8 后重新核算 Q9。同时，把上下文溢出记录为独立失败状态，保存 `q8_raw`、预算和失败原因，避免一个动作的预算异常抹掉生成证据。不应使用 GT 回填，也不应依靠上游静默截断。

还应在原 tokenizer 环境补一个接近容量上限、带合法解释文字的 Q8 测试。**我没有把历史上“五点 Q9”的格式失败归因于这个问题。**

### 3. P2：比较报告声称报文不变，但实际上没有比较报文

**位置：`src/planning/compare_evidence.py:35–54`。**

比较入口检查了特征、帧、运动状态、`evidence_full.json` 和编码往返一致性，但没有读取 P/F 的原始请求、响应文件，最后却直接写入：

```python
full_wire_unchanged=True
```

这不是“证据不足以判断”，而是报告字段的结论强于代码实际完成的检查。

**为什么 evidence 相等不能替代 wire 相等？** P 报文包含 `history_scores`，但 `make_evidence()` 保留历史时只复制 `history`、`history_valid` 和 `history_times`，没有保留完整历史分数。这个转换本身就不是一一对应的。

我构造了两份合法 P 报文，仅将一个非当前时刻的历史分数从 `0.8` 改为 `0.9`。两份报文字节长度同为 1433，但内容不同；通过现有证据构造路径、使用测试预测器，得到的 evidence 完全相同。因此，当前检查无法推出 `full_wire_unchanged=True`。

**最小修复与验证：** 直接读取并比较对应的 request/response 字节，或计算并比较内容哈希；另行验证报文与保存的 evidence 对应。缺少原报文时应报告“未检查”，而不是 `True`。增加“报文不同、evidence 相同”的负例测试。

这不证明历史报文一定不同；它证明的是**当前比较入口不能独立支撑自己写出的这一结论**。

### 4. P2：相对 checkpoint 路径会生成失效软链接

**位置：`src/planning/v2vgot.py:165–172`，`local_adapter()`。**

代码先用当前工作目录解释 `checkpoint / name`，检查源文件存在，然后直接：

```python
destination.symlink_to(source)
```

当 `checkpoint` 是相对路径时，软链接中的目标路径会相对于 **adapter 所在目录**解释，而不是相对于原工作目录解释。因此，源文件检查成功并不能保证链接有效。

**触发条件与后果：** 使用类似 `resources/checkpoint-4330` 的相对 checkpoint 路径，并首次创建本地 adapter。加载器随后会看到不存在的链接目标。

我在临时目录中直接运行了该函数片段，确认了“源文件存在、软链接创建成功、软链接无法解析到文件”三个条件同时成立；没有加载任何模型权重。

**最小修复与验证：** 创建链接前把 checkpoint 和 CLIP 路径规范化为绝对路径，例如先执行 `expanduser().resolve()`。测试应同时覆盖绝对路径和相对路径，并检查生成链接的 `is_file()`，而不只是 `is_symlink()`。

### 5. P2：成本账本把未执行 MTR 的回退目标算成模型计算目标

**位置：`src/tools/vehicle.py:92`；对照 `cmp_adapter.predict()`。**

`cmp_adapter.predict()` 只对至少有两个有效历史状态的目标执行 MTR。短历史目标使用回退预测，并明确标记 `model_used=False`。但服务端成本字段使用的是：

```python
model_targets_computed = len(w['track_ids']) if model_seconds else 0
```

因此它统计的是窗口目标总数，而不是本次真正执行模型的目标数。

**触发条件与后果：** 邻车窗口中有刚出现、仅有一次有效历史的目标时，计算量账本会偏大。我用两条短历史目标验证：响应中使用模型的目标数为 **0**，`model_targets_computed` 却为 **2**。

这不影响已经按 wire 计算的字节数，也不意味着所有成本记录都错误；问题是这个具体字段不能表示它声称的“模型计算目标数”。

**最小修复与验证：** 非缓存计算时根据预测结果的 `model_used` 统计真实模型目标数，并单独记录回退目标数、返回目标数。测试覆盖全部回退、部分回退以及缓存命中三种情况。

## 二、两个需要单列的研究边界，不应混成“默认路径已经有 bug”

### ROI 查询不能直接沿用全量 P/F 的同信息等价结论

F 的实现是**完整提供方上下文预测，再过滤 ROI 输出**；P 则先返回 ROI 内历史，接收方根据返回目标重建窗口并预测。相同 ROI、相同返回目标，并不意味着预测器看到了相同上下文。

用仓库测试中相同类型的上下文敏感预测替身，我验证了：ROI 内同一个目标，P 本地重算看到 1 个目标，F 看到 2 个目标，因此预测不同。

**这不否定默认无 ROI、完整 P 历史的等价对照。** 当前文档本来也把同信息对照限定为完整历史。需要防止的是后续查询策略实验把这个结论直接外推到 ROI 场景。建议在报文或实验元数据中显式记录预测上下文范围，并让同信息检查验证这一条件。

### `history_valid` 是否等于“该时刻有真实检测观测”，还缺上游验证

当前跟踪导出保存的是 `tracker.track()` 返回的目标状态，没有保留“该帧是否与检测匹配”的标记；`make_window()` 只要看到该 track 出现在输出中，就把对应历史位置设为有效。

因此代码目前直接保证的是“该时刻有跟踪输出”，不一定是“该时刻有检测观测”。**我没有取得当前外部 AB3DMOT 版本的实际输出策略，不能断言它一定输出了未匹配的预测状态。**

最小验证办法是在完整跟踪环境中人为断掉一帧检测，观察该目标是否仍被输出、是否进入 P 历史、`history_valid` 是否仍为真。若存在预测维持状态，应区分 observation mask 和 estimated-state mask。即使状态是因果的，也不宜把两者在协议中混称为观测。

## 三、已读代码中做得比较扎实的部分

**在线与离线职责分离有实际实现。** Ego 特征读取限定当前帧与上一帧；窗口构造只使用历史区间；邻车窗口加载延迟到 query；未来 Ego 位姿读取位于独立离线标签准备路径。这轮没有在已追踪的在线主线中发现未来 GT 被直接送入规划器的路径，但这不等于预训练来源独立性已经证明。

**Q9 的生成父上下文和监督掩码并非只写在文档里。** 在线 Q9 使用真实 `q8_raw`；监督样本构造会核对生成父回答；前缀标签设为 `-100`，原 vendor 多模态准备函数也对插入的特征位置使用忽略标签。原语言模型的生成和监督 forward 路径确实被调用，而不是生产路径中的测试替身。

正式适配训练、查询控制器、规划质量、预训练来源核验和 CUDA 算子一致性，仓库已经明确区分为未完成或未验证事项；我没有把这些重复算成上述实现缺陷。
