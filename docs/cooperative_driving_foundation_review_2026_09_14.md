## 1. 结论与上一轮建议的修正

**当前 ToolV2X 已形成真实工具调用链，但尚未形成与该调用机制相匹配的协作驾驶基础。** 不足不能仅用“样本少、训练不够”解释，也不能靠扩大 receiver 目标覆盖解决。

上一轮“对齐指标、补实体表、再测固定 F”的建议仍不充分：实体表解决身份组织，不能自动让规划器学会利用证据。下一版需要同时明确**实体关联、状态/预测表示、入模接口、轨迹输出、监督与评价**。这是一个有明确边界的驾驶端改造，不是重做全部感知/预测系统。

建议优先研究：**保留原 GoT 的多模态骨干与本地点云输入、保留原 MTR 的远端能力，建立实体级 P/F 编码和共享驾驶输出。** 标准关联、编码器、轨迹头均作为基础组件，ToolV2X 的贡献仍须来自任务参数化与真实修订反馈组织下一次远端能力调用。

当前结果不足以选择最终网络，也没有证据保证上述改造一定产生协作增益。它给出了比继续调整文本装包更明确的能力建设方向。

## 4. 必须落实到系统里的设计认识

### 4.1 身份关联、状态融合、预测融合是三件事

UniV2X 给出显式匹配与融合路线；Co-MTP 在历史预处理后仍保留多源节点，说明关联后不必抹掉来源。两者共同支持“统一实体身份，同时保留观测差异”，不是按 track_id 合并字典。[UniV2X](https://arxiv.org/html/2404.00717v2#S3.SS4)、[Co-MTP](https://arxiv.org/html/2502.16589v1#S3.SS2)

建议将 receiver 生成的物理实体表示定义为：

| 内容 | 含义 |
|---|---|
| entity_id | 本 episode 的物理目标身份，不冒充全局 GT ID |
| aliases | 本车/邻车的 source-local track handle 与关联关系 |
| role | ego / peer / other / unresolved；自车检测不能默认作为外部障碍 |
| observations | 各源当前框、历史状态、时间、valid mask、score，保留原始来源 |
| forecast_sets | 每个来源/上下文的多模式轨迹及分数，记录是 provider 返回还是 receiver 派生 |
| association_status | confirmed-by-rule / ambiguous / unmatched 等可解释状态，规则版本可追溯 |
| parent_refs | 所有实际影响这个表示的合法本地/已购字段 |

首次实现可采用时空几何门限与一对一 Hungarian 匹配，依据当前框及共同有效历史的残差，不需要训练额外匹配网络。门限、成本权重、平局规则应有确定规格；实验数值进入版本化执行配置。发生歧义时保留来源与不确定关系，不能为了减少对象数强行合并。

自车识别应使用当前 ego 几何、姿态及合法历史一致性；只删除“近原点”的所有目标会误伤近距离他车。peer 身份若需要额外车辆元信息，必须来自已允许的定位/通信元信息或付费返回，不能偷读未知私有目标表。

状态融合首先建立一致的实体集合和缺失 mask；数值估计可以采用清晰的质量规则或学习融合。检测分数不是方差，不能直接冒充逆方差权重。P 中有效历史是 **causal tracking-state motion proxy** 的输入，包含跟踪器因果维持状态，不等于逐帧 detector hit。

### 4.2 F 必须以多模式、带来源的未来信息参与驾驶

CMP 的论文聚合预测分布；本地 `MotionAggregatorTransformer` 确实按 `center_objects_id` 收集各车模式后重新解码。但这并不是可直接调用的跨车目标关联器：它预先要求共同对象身份，并在该实现中只遍历 ego 已有中心对象。[CMP](https://arxiv.org/html/2403.17916v3#S4.SS4)

本地代码还提示四个接入前提：

- `MTR/tools/cfgs/v2v4real/v2v4real_multiego_cobevt_c256.yaml:133` 选择 Transformer aggregator；当前 ToolV2X 加载的是 no-cooperation MotionTransformer。
- `MTR/mtr/models_v2v4real/multi_ego_mtr_model.py:1073` 使用 BEV 特征，map 分支被注释；不能把论文公式中的全部 map 路径说成这个本地配置已运行。
- 同文件 `:1456` 起从一次 batch 的各 CAV 输出整理预测；非 ego 分支将第一预测位置清零。单看这段代码不能证明完整执行了论文中的前一物理帧通信延迟。
- `MTR/mtr/datasets/v2v4real_multiego_dataset.py:573` 按历史与未来 GT 可用性筛选对象，`:596` 求 GT/pred ID 交集。适合作为原任务数据处理参考，不能用来决定在线请求前可见目标。

建议首先在实体内保留多个 forecast sets，让普通 attention 学习整合到驾驶表示。不要将两种不同机动的坐标平均成中间轨迹，也不要认为不同来源的第 1 模式是同一机动。若需要输出统一预测分布，应另有预测监督与模式处理规格，不能把它悄悄塞成一次工程修复。

当前 F wire 不含完整协方差。首版可以使用“带模式权重的轨迹集合”，不必立刻扩报文，但不能声称是完整概率占用或校准碰撞风险。若以后增加 GMM 参数，需要同步修改服务契约、wire 成本、坐标变换与同信息对照。

### 4.3 P 和 F 应有直接、不同且可组合的驾驶入口

建议明确三条合法路径：

1. **P-state/history → 实体观测表示 → driver**：P 可以直接改善已知目标状态或补充远端独有对象，不强制先预测。
2. **P → receiver 本地 MTR → derived forecast → driver**：这是可选本地计算路径，另记计算成本及输入上下文。
3. **F → 实体的远端 forecast set → driver**：预测与已有/随包返回 anchor 关联，不替换成另一条观测历史。

若 ego 与 P 的观测进一步联合输入 MTR，这是新的 `ego_plus_acquired` 上下文，不等于 F 所用的 `peer_full`。它可以作为额外工程能力，但**不能用其输出做 P/F 同信息等价证明**。同信息检验必须保留独立的源内 full-P 重算：相同完整 peer 输入、时刻、排序、mask、模型和精度。

请求轨迹影响 F 目标选择，仍不意味着 MTR 在预测他车对该轨迹的反应。Co-MTP 的条件预测模型不同，并且论文明确使用真实未来轨迹经曲线插值构造 AV planning 条件；只能借鉴编码思想，不能复制该输入到本项目在线服务。[Co-MTP §III-A](https://arxiv.org/html/2502.16589v1#S3.SS1)

### 4.4 编码与轨迹输出必须一起选择

| 路线 | 完整内容 | 判断 |
|---|---|---|
| A：规范实体文本＋原 Q9 | 做关联与结构化摘要，按新格式重新适配原文本轨迹输出；保留几何诊断 | 改动最小，值得保留为基础对照；仍依赖数值文字理解与 token 监督 |
| B：实体数值编码＋GoT＋共享数值轨迹头 | 分别编码观测/历史和多模式预测，投影到 GoT；规划 token/hidden state 输出六点轨迹，接受轨迹监督 | **推荐的主要改造方向**；直接补足入模和执行接口，但需要训练与完整实现设计 |
| C：完整换为 UniV2X/VAD/CoDriving | 迁移感知、地图、规划与训练数据接口，再接工具查询 | 工程和任务语义变化大，难以隔离当前机制；本轮不推荐替换底座 |

B 的依据分别来自对象向量对齐、LLM 数值执行和 agent 的运动头，而不是“加网络看起来更高级”。[Driving with LLMs](https://arxiv.org/html/2310.01957v2#S3.SS4)、[LMDrive](https://arxiv.org/html/2312.07488v2)、[DriveAgent-R1](https://arxiv.org/html/2507.20879v3)

建议 B 中只使用普通时序/集合编码与 MLP，不引入新预测骨干。保留本车原点云特征供道路/场景理解；P/F 的数值 tokens 只能来自实际合法证据。不要把未购买的 peer BEV 或中间 hidden features 随便作为“融合上下文”读取。

所有阶段和所有固定/单轮/交替对照共用同一个完整驾驶模型：`D = 编码器 + GoT + 轨迹头`。轨迹头必须以 GoT 表示为条件，不能旁接一个完全独立的 planner 产生修订，再宣称 GoT 驱动了反馈。需要有移除 GoT 条件的诊断对照，检验是否绕过主干。

**这会改变当前 direct Q9 字符串轨迹的实现规格。** 保留 GoT 骨干不等于保持原 QA 头完全不变；其输出接口、训练、预算和 same-evidence 控制要重新具体设计并经用户确认。本文没有将它偷偷视为已经批准的 T9 后续小改动。若最终坚持原 Q9 输出，则选择 A，并明确其训练只能直接优化答案 token，不能声称有可微坐标损失。

### 4.5 训练要覆盖“证据如何被用”，不是只延长旧训练

Where2comm 训练不同轮次/带宽，CoDriving 的规划训练覆盖不同信息选择率。它们给出的共同参考是：后端需要适应真实的信息缺失与融合条件。[Where2comm](https://arxiv.org/html/2209.12836)、[CoDriving](https://arxiv.org/html/2404.09496)

建议训练组织分清两件事：

- **先建立共享 driver 的证据使用能力。** 同一基础帧构造 Ego、P observations-only、P-local、F、PF 的合法输入，覆盖缺失历史、远端独有对象和多来源预测。训练与部署采用同一编码器、mask、身份处理及预算规则。
- **再训练查询决策。** driver 冻结后，才用实际返回、实际修订与终态损失产生价值监督。真实阶段 1/2 的分布也应被共享 driver 的适配考虑，不能只训练旧的固定格式。

对于路线 B，最基本的驾驶损失是六点轨迹的 L1/SmoothL1；几何约束可借鉴 VAD，但只能在对应对象/道路标签可靠、定义完整时添加。没有道路边界就不宣称训练了道路约束；预测轨迹之间的冲突代理也不是实际安全真值。[VAD §3.3–3.4](https://arxiv.org/html/2303.12077v3#S3.SS3)

观测/预测编码可采用掩码重建、当前对象定位/运动状态等辅助监督来建立数值对齐。此处是候选，不能将每项都自动加入；应优先复用已有观测标签，避免新建大规模语言标注工程。

同一帧不同 evidence 对应同一个真实 ego future，是正常监督设定，不能为了让 F 显得有效而伪造不同轨迹标签。但若训练只需依赖 ego 速度就能拟合，网络可能忽略协作输入。需要状态-only、去证据、正确/错配证据等诊断，并在真实交互场景报告结果。错配证据属于控制实验，不是正常在线报文。

“去掉证据后结果改变”也不充分：改变可能是不稳定性。需要确认变化方向与可观测几何关系一致，并在独立数据上带来任务收益。纯合成案例只证明接口/基本敏感性，不能作为真实驾驶效果证据。

### 4.6 评价首先明确任务，再谈论文数字

| 评价对象 | 应报告什么 | 禁止混写 |
|---|---|---|
| 官方 GoT 任务 | 官方样本/车辆角色/上下文来源/生成顺序与原评测归约 | 本项目两帧 direct 输出比论文全测试集“更好” |
| ToolV2X 受限轨迹任务 | 固定因果输入、固定同帧标签的 3 秒轨迹误差与失败率 | 自动等同完整 GoT 或闭环驾驶 |
| CMP 预测任务 | 对他车六模式预测的 minADE6/minFDE6，明确 horizon/目标集合 | 拿它与自车单条轨迹 ADE/FDE 直接排名 |
| 驾驶几何诊断 | 独立未来对象标签下的碰撞/最小间距，可靠道路标签下的越界；附有效性与舒适性 | 用 F 自己的预测评价 F 自己带来的安全收益；把轨迹接近人类等同安全 |
| 驾驶执行评价 | 真正控制展开后的安全、进度、舒适与失败；明确非反应式或反应式 | 把静态六点检查称为 NAVSIM/闭环 |

本地 GoT 上游脚本 `LLaVA/scripts/eval_v2v4real_3d_grounding.py:736` 将 1/2/3 秒 L2 定义为前 2/4/6 点误差均值；当前 `src/evaluation/planning.py:19` 的 `L2_1/L2_2` 是端点，`ADE3` 是六点均值，`FDE3` 是末点。故 GoT 的 L2@3s 对应完整有效六点下的 ADE3，不是 FDE3。统一归约后仍需统一样本、输入和模型，不能只换列名。

状态-only 捷径与评价局限有直接文献支持，但还需在本项目定位，不能照搬其他数据集比例。[Is Ego Status All You Need](https://arxiv.org/html/2312.03031)、[NAVSIM](https://arxiv.org/html/2406.15349v2)

最少保留一张全预声明测试集主表，另做转向/减速/交互/遮挡的预声明分组。分组不能按“F 改善了哪些帧”倒推，也不能剔除无收益场景后称全局提升。按录制组划分并报告相关性；不得将相邻帧当独立样本增加显著性。

完整官方 GoT 复现应与因果 ToolV2X 评价单独命名。若官方 QA 用未来构造的参考计划，原基准条件可以在单独复现中如实说明，但不能作为部署输入或与因果方法不加说明地比较。

## 5. 保留主线的完整信息流建议

```text
时间 t 本车点云 / 跟踪历史 / 合法任务条件
                |
        本地实体与预测表示
                |
     共享驾驶模型 D --> 初始轨迹 tau0
                |
        带 tau0 的 P/F current 请求
                |
  邻车私有上下文执行 --> 真实字段 / receipt
                |
    已购账本 E + 可选本地派生（有 parent refs）
                |
  因果关联 / 自车角色 / 状态与多模式预测融合
                |
       共同入模表示 Z（依赖可追溯）
                |
     同一 D --> 实际修订轨迹 tau1
                |
  用实际 tau0/tau1 + 合法证据决定 change/current/STOP
                |
       至多再执行一次 P 或 F
                |
    同一套更新与 D --> tau2 / STOP
```

E、派生账本和 Z 必须保持区别。融合结果可以改变 planner 的表示，但不能改写 provider 原始返回或制造 receipt。若某个未显式展示的字段参与了关联、权重或融合，它就是最终表示的依赖，需在 Z 的来源闭包中记录；不能以“没有直接显示在 prompt”将其隐去。learned token 压缩也必须算真实 token/计算与父字段成本。

本车原始输入保持相同，不意味着合作后每个 fused entity token 必须与 Ego 完全相同；融合本来就应更新表示。旧合同中的“本车文本块逐字不变”要留给旧基线，新数值路线应改成“本地原始输入固定、共享变换固定、远端增量来源清楚”。这是需要正式改规格的地方。

候选需要完整覆盖两种协作价值：**P 改善当前可观察场景，F 提供基于邻车私有上下文的未来估计**。如果 driver 只认一种统一 forecast 行，而无法单独使用位置/历史，主线中的 P/F 能力差异就被实现消解了。

## 6. 哪些可以写成贡献，哪些只是必须补齐的基础

| 类别 | 内容 |
|---|---|
| 核心研究假设 | 实际首次返回导致驾驶方案改变，以改变后的驾驶需求组织第二次 P/F 任务，比强单轮委托或固定两步取得更好的质量—总成本关系 |
| 标准工程/学习基础 | 时间坐标、实体关联、自车识别、观测/预测编码、共享融合、轨迹头、监督对齐、检查点与版本记录 |
| 实验控制 | 旧 Ego/P/F/PF/rule；新共同 driver 下对应固定配置；current-only、冻结/交换 tau1、strong conditional one-shot、same-evidence extra-generation、完整 P 本地重算 |
| 当前不做 | 新 RSU/I、替换预测骨干、联合 RL、为了数量增加工具、peer 学习排序器、额外世界模型、用新规划器绕开 GoT、长期训练替代接口设计 |

CoDriving 已有规划请求，Where2comm 已有融合后反馈，MATE 已有远端任务执行，DriveAgent-R1 已有工具推理。因此“加了融合与轨迹头”补足方法可信度，**不会自动补出创新点**。current/change 的具体作用和净收益依旧需要公平对照。[CoDriving](https://arxiv.org/html/2404.09496)、[Where2comm](https://arxiv.org/html/2209.12836)、[MATE](https://arxiv.org/html/2303.06080)、[DriveAgent-R1](https://arxiv.org/html/2507.20879v3)

strong one-shot 不能只用固定 PF 代替：它应能在 peer 私有上下文中执行与预算相同的合法条件程序。但它不能免费获得首次返回后 ego 的新 GoT 轨迹；若为了模拟它传输 ego 私有状态或执行额外 driver，必须计入信息与计算。比较可允许成本构成不同，但要报告共同总预算下的质量曲线。

same-evidence extra-generation 应固定实体表示、模式集合和编码器，给相同次数/预算的再生成或修订机会。若数值头是确定性前向，重复完全相同输入本来就可能完全相同；不能把这种弱控制冒充充分的额外推理控制。要定义有实际作用的、所有方法一致的修订输入/解码规则，并计入各次 GoT、头、融合、预测、网络成本。旧 2 帧 one-shot 是诊断，不具备这一公平性。

三次 GoT 的耗时不能只算最后一次。固定时间 t 的三次方案修订仍是开环决策内部循环，不是三个车辆运动时刻；若声称实时部署，必须进一步处理整轮计算期间车辆运动与证据时效，不能拿当前单机冻结重放直接作实时结论。

## 7. 推荐的下一批工作及完成标准

本轮交付研究，不启动下列实现/训练。下一批应作为一个整体驾驶端计划，避免每补一处接口就转去积累论文误差表。

| 顺序 | 具体交付 | 完成后能回答的问题 |
|---|---|---|
| 1 | 锁定受限驾驶任务、官方兼容指标、样本/标签/角色、可用导航与道路信息；明确路线 A/B | 到底在评价什么，是否允许与 GoT/CMP 对比，以及需要哪些标签 |
| 2 | 对 UniV2X 的实体模块与对象向量编码原代码定向复核，输出可复用模块/必要改写/输入缺项；同步完成 P/F 实体结构设计 | 原有框架哪些实现可借鉴，哪些会带入 GT/地图/远端特征权限问题 |
| 3 | 一次性实现共同实体表示、P/F 分型编码、共享 driver 出口及训练接口；旧路径保留 | P 位置/历史和 F 多模态未来是否都真正到达可训练驾驶通路 |
| 4 | 在单个集成批次做几何/身份/因果/梯度/序列化回归和小批数值适配检查 | 连接、损失、掩码与训练方向是否正确；此步不能宣称驾驶收益 |
| 5 | 接口固定后，训练共享 driver 的证据使用能力并在未参与选择的场景评价固定配置 | 协作证据能否改善驾驶，哪些场景及失败模式需要修正 |
| 6 | driver 冻结后恢复 current/change 与价值模块的正式比较 | 收益来自工具调用组织，还是仅来自新 receiver、更多信息或更多计算 |

步骤 1/2 可以并行准备，步骤 3 应交付可训练的完整连接；不能无限切成边缘补丁。训练长度应由正确适配后的验证曲线决定，不能现在沿用旧输入再追加若干小时。

步骤 1 需要明确一个可能影响论文任务的问题：当前没有显式 route command。若数据没有因果可用导航，首版应准确称为“短时 ego 轨迹模仿/规划基准”，不从未来 GT 提取转向命令。后续若要做更一般的路线决策，再选择带合法任务条件的评价设置。

## 8. 尚未被本轮研究解决的问题

1. 当前两源坐标链已实现，但标定/跟踪误差下实体关联精度与近原点对象真实身份仍需验证；本报告没有根据距离直接判定或删除对象。
2. 新数值编码能否在当前标签规模与分布下学会使用远端证据，需适配后判断；文献只是设计依据。
3. 轨迹头是否保留足够 GoT 条件作用、如何选择规划 hidden state、如何兼容再生成控制，需步骤 2/3 的具体实现规格。
4. 道路/导航/目标未来标注的因果输入与离线标签可用性尚未完成新清单；不能借未来标签填在线缺口。
5. 基础模型原始预训练/检测缓存的数据来源限制仍在；不能据开发集结果宣称未见场景泛化。
6. current/change 是否比强单轮或 current-only 多出值得发表的增量，仍未证明。基础完整使这个问题可检验，不保证答案为正。

建议的立即决策是采用以上整体驾驶端改造方向，并优先核对前两份参考源码。最终路线 B 的接口和训练改动应在具体设计中确认；在此之前保持现有实验归档与旧基线，停止把装包联调当作方法效果推进。
