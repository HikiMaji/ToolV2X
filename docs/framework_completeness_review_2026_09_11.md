# ToolV2X 完整框架对照与补齐顺序

日期：2026-09-11。当前请求：参考其他工作的完整框架，重新判断整体完成度，以及现有数据对后续实现的用途。

本次核对论文正文、目标设计、实际调用代码和配对数据文件，只完成审查与顺序修订，没有启动模型训练、生成或数据重建。下面的实现建议不代表最终查询机制已经确定，也不替代完整的函数级实现规格。

## 1. 需要纠正的是整体推进顺序

用户希望先建立能够共同工作的完整框架，再在这个框架中做训练和实验。不能把这一要求缩成只训练 Ego，也不能继续以固定 F 的正负结果作为当前主要交付。

目前已有原能力模块、真实 P/F 接口、驾驶生成入口和监督准备，但尚缺统一的工具决策执行过程，以及与它匹配的完整训练和评价运行。无法用“完成了一半”这样的比例准确描述；更准确的状态是：组件已经部分接通，完整可训练的 ToolV2X 基线尚未完成。

原 [framework_design.md](framework_design.md) 第 4、6、9 节已经提出调用、证据更新、终止、训练和评价。问题主要是实施顺序把这些职责拆开后，统一任务运行持续后置。应以完整运行链路为下一项交付，再逐项改善模型质量。

## 2. 完整框架可以向谁借鉴

| 参考 | 原工作如何形成完整任务 | 对 ToolV2X 的启发 |
| --- | --- | --- |
| [DriveAgent-R1 v3，§2](https://arxiv.org/html/2507.20879v3#S2) | 从初始视觉及车辆状态选择推理模式；工具请求被执行，返回证据进入历史，再继续或结束；领域对齐、两种模式的监督示范、能力强化和模式选择训练相互配套 | 借鉴状态、动作、工具结果、终止与训练过程的对应关系。其主任务是行为序列，三秒轨迹头属于扩展；不能把它误读为现成的远端 P/F 轨迹规划器 |
| [V2V-GoT v4，§III–IV](https://arxiv.org/html/2509.18053v4#S3) | 多车当前/上一时刻感知特征与 Q1–Q9 任务图共同输入模型；训练数据按任务和父子上下文构造，推理沿图使用上游生成回答；投影层与 LoRA 接受任务训练 | 复用点云特征、模型和监督接口，同时明确原图中被替换的职责由谁承担。只保留原模型类或 Q9，并不能继承完整 GoT 方法 |
| 本机 CMP 原 MTR | 当前实际复用的是原运动预测分支，经因果跟踪窗口适配后生成目标预测 | 作为 P 本地计算和 F 服务的能力组件。它没有替 ToolV2X 完成调用决策、接收器训练或本车驾驶训练，也不等于完整 CMP 已复现 |

这些是对框架组织方式的借鉴。DriveAgent 的 RL、GoT 的全部 QA 节点不必逐个复制；要明确承担它们在本项目中仍然必要的职责。GoT 原流程涉及的 GT 未来上下文不能被恢复到 ToolV2X 在线输入中，已有 [因果边界](framework_design.md) 继续适用。

## 3. 代码中已有什么，缺什么

| 职责 | 当前真实实现 | 距离完整框架的缺口 |
| --- | --- | --- |
| 本车输入与远端能力 | [inputs.py](../src/planning/inputs.py)、[cmp_adapter.py](../src/prediction/cmp_adapter.py)、[vehicle.py](../src/tools/vehicle.py) 已读取真实特征、运行原 MTR、序列化 P/F | 不需要为这轮重新发明预测器；沿用来源与时间约束 |
| 谁决定请求什么 | [run_connection.py](../src/planning/run_connection.py) 第 110–123 行按外部指定动作枚举工具；[paired_inputs.py](../src/planning/paired_inputs.py) 固定查询 F | 缺当前状态到 STOP/P/F 与 ROI 的实际决策入口；工具支持 ROI 不等于策略会选择 ROI |
| 收到结果后如何继续 | `make_evidence` 能将已收到报文变为带来源的证据 | 缺统一执行器在每次真实结果到达后更新状态、再次调用策略及执行停止规则；预定 PF 不能表示结果驱动的第二次请求 |
| 证据如何进入驾驶模型 | [v2vgot.py](../src/planning/v2vgot.py) 的 `plan` 使用混合 `fit_evidence`；配对数据另用 `fit_local`、`fit_remote` 保持本车文字一致 | 两个入口不能直接互换。若用新配对样本训练、再走旧 `plan`，会重新选择目标和组织上下文；需统一训练与推理的输入构造 |
| P 的接收方式 | 当前 `make_evidence` 遇到 P 会运行本地预测器；返回历史也保留 | 这是现有基线路径。P 的工具定义只负责观测，接收器应明确允许哪些使用方式；不能把 P 必经 MTR 当作所有方法的定义，也不删除它作为强对照 |
| 驾驶模型训练 | 有原监督编码、一次更新和重载检查；配对数据已准备 | 缺覆盖完整基线使用状态的正式训练运行，以及对应的保存、选模和真实生成评价；一次更新检查不是训练完成 |
| 完整运行评价 | [evaluation/planning.py](../src/evaluation/planning.py) 能评价保存的轨迹；工具有真实报文字节记录 | 缺统一记录一次任务中所有调用、证据变化、停止原因、最终输出与失败，再离线连接质量与总成本的运行结果 |

证据选择是已确认的入口差异，不是本次新发现的模型性能故障。它说明“局部数据准备通过”不能自动推导“完整训练与推理已经一致”。

## 4. 下一版完整基线应实际跑什么

保留两车、P/F、原 MTR、原 GoT 驾驶主体及三秒六点任务。完整运行至少包含：

```text
本车当前/历史输入及本地预测
        ↓
当前任务状态：本车信息、已收到证据、调用历史、剩余预算
        ↓
决定 STOP 或查询 P/F，并给出合法查询区域
        ↓ 查询
远端真实执行 → 校验报文 → 更新已获得的证据与成本
        ↓
回到决策入口，使用实际结果继续或停止
        ↓ 停止
统一驾驶模型生成本车轨迹
        ↓
记录完整过程；独立离线评价质量、失败与成本
```

这里的交互发生在同一个决策时刻内，不能称为车辆动作已经改变环境的闭环驾驶。

固定 Ego/P/F/PF 对照也由同一执行器运行，只是动作预先给定。第一版调度可以采用明确、读取当前已获信息的简单规则，使选择、更新和停止都有实际实现；它仍是规则基线，不是学会调用的最终 agent。训练型调度以后替换同一决策入口，避免重新搭一套实验路径。

若查询依据初始驾驶方案，方案必须由当前模型和本车合法输入产生，记录其执行成本；失败处理需在各条件中一致。使用哪一种查询规则属于基线配置，不在本报告中提前认定为最终机制。

完整框架还需要明确三类接口的共同约束：

- 请求：提供者、决策时刻、工具、ROI；只能依据当前可用信息寻址。
- 结果：P 的观测或 F 的预测，连同来源、坐标、时间、可用性和实际成本；空结果保留。
- 驾驶输入：由同一个入口根据当前合法证据构造；目标选择、数值编码和预算在训练、验证、实际任务运行之间一致。

现有 source 分离与 compact 编码可以继续作为基线。框架完整并不要求立即新建融合网络，但必须明确未关联目标、冲突来源、历史缺失及容量不足时到底给驾驶模型什么。

## 5. 训练怎样与这条流程配套

| 部分 | 首版处理 | 样本与训练含义 |
| --- | --- | --- |
| MTR 能力 | 复用当前冻结权重 | 当前阶段无需因执行器补齐而重跑预测调参 |
| 驾驶模型 | 复用原 GoT 的投影层、LoRA 与轨迹监督接口，覆盖基线实际使用的证据状态 | 包含无远端信息、收到 P、收到 F 及合法组合；训练输入使用与运行时相同的构造器，目标仍为隔离的本车未来轨迹 |
| 初版规则调度 | 不训练 | 对规则的调用过程做真实执行记录；规则动作不能标成最优调用标签 |
| 后续学习调度 | 在同一完整运行路径上定义训练目标后实现 | 样本需要查询前状态、动作/区域、真实结果和停止过程；离线效用只作训练信号，不能进入在线输入。当前两条件最终轨迹样本没有提供这些监督 |

调用策略最终选监督学习、LLM 工具调用还是 RL，仍是后续方法选择。现在需要先把它们将作用于哪种状态、改变哪种动作、如何接受评价定义清楚。不能因为还没有选择 RL，就把状态更新与执行器也一直后置。

本轮现有 direct 六点任务可作为驾驶输出基线；是否需要行为中间层应由完整设计说明其作用。不会仅为恢复论文外观而机械补回全部 Q1–Q9，也不会把少一个 QA 节点直接当作框架不完整。

## 6. 现有数据的具体用途

已直接检查 `outputs/paired_driving_data_v1/preparation_result.json` 与导出行：5974 条训练样本、216 条验证输入；训练行任务为 `Trajectory`，包含提示与最终轨迹答案，未执行驾驶训练或生成。

| 已有产物 | 是否仍有用 | 使用条件 |
| --- | --- | --- |
| 因果观测索引、源内历史、本车特征 | 可继续复用 | 维持源、时刻、坐标与划分定义；已有断点隔离理由继续保留 |
| 完整 MTR 数组与原始 P/F 报文 | 可继续复用为组件证据及回归材料 | 区分完整原结果与模型真正读到的截断内容；不能免费读取未查询远端数据 |
| 本车六点离线标签 | 当前轨迹任务下可继续复用 | 若任务时间跨度或坐标定义改变，再按新定义生成 |
| 现成 Ego/F 提示及训练行 | 可用于对应的固定条件适配；最终格式可能需要重新导出 | 不能绕过统一输入构造，也不能直接代表完整工具调用训练数据 |
| 单帧驾驶与一次更新检查 | 保留为接口诊断和历史失败记录 | 不用于证明完整框架性能或方向成败 |

因此，已有数据不是全部无效；它们的有效范围比完整 ToolV2X 方法窄。应保留可复用原料，让整体设计决定最终训练样本，而不是继续围绕临时提示批量生产数据后再决定模型怎样用。

## 7. 具体补齐顺序与完成标准

1. **收敛一份整体实现规格。** 以原设计为基础，明确模块职责、请求/证据/状态、统一驾驶输入、监督目标、终止和评价。下一步的函数级规格只覆盖这条运行链，不增加并行骨干或训练矩阵。
2. **实现同一套完整执行与输入路径。** 复用 `VehicleTools` 与原驾驶模型，补齐决策—执行—更新—停止；统一 `plan` 和配对数据的证据构造。固定对照与规则策略通过同一条路径运行。
3. **把这条路径接到正式训练及评价。** 复用现有监督编码和原可训练参数路径，保存可重载模型；按同一输入约定导出所需样本。训练数据设计同时覆盖本车和协同状态，不能再次缩成只完成 Ego。
4. **用少量真实完整任务调通，然后在该框架下完成基础适配。** 功能覆盖无调用、P、F、两次调用、提前停止及空结果，保留原始调用和生成。少量任务只作整体调试，不能宣布协同收益；基础训练与多帧评价仍需真实完成。

框架验收看关键职责是否共同工作、训练和推理是否一致、结果是否能追溯到实际输入。单元测试、一次更新或结构图不能替代这些证据。基础质量验收会使用轨迹误差与失败记录，但不要求把 F 调到一定优于 Ego 才允许通过。

完成上述工作后，再在稳定框架上研究调用机制与性能改进。当前单独 Ego 训练以及直接拿固定 F 表格当下一科研节点的建议都不再作为自动推进顺序。

本次文档已核对上述职责与代码入口的对应关系、已实现/未实现边界、旧数据的复用条件。尚未形成最终函数级实现规格，未宣称新执行器、统一训练或学习调度已经完成。
