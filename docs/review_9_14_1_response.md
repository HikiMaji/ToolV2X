# 9-14-1 复核：能力语义、现有实现与下一步

日期：2026-09-14。性质：对 [9-14-1](9-14-1.md) 的阅读与代码复核；**不修改该输入材料，不变更运行代码，不启动训练或新方法实验**。

## 1. 结论

**采纳“先写清远端能力和反馈贡献”的提醒，但不采纳“必须现场重跑模型才是 Tool”，也不把当前 P/F 重定义为按需检测/跟踪和 ego-plan 条件反应预测。**

9-14-1 正确指出，GoT 的存在与否不能决定 ToolV2X 的成立；实体关联、融合和轨迹头应服务返回值使用，不应替代调用机制的贡献。前一份架构报告较多篇幅讨论编码器，容易使优先级看起来倒置，需要把下面的一页能力规格放在驾驶端设计之前。

但材料中对 P/F 的部分描述不符合当前代码，也与 9-12-2 的明确边界冲突。沿用这些说法会制造尚不存在的能力，或为了名词增加无意义计算。现有协议已经具有任务执行与真实返回，当前真正欠缺的是可靠的驾驶证据使用能力和反馈净收益证据。

此次校准不需要重建缓存、重训 MTR、增加工具或暂停整个方法推进。结构化驾驶器仍是主候选，尚未实施；GoT 仍可保留为旧基线/备选。

## 2. 对材料逐项判断

| 材料观点 | 判断 | 当前代码与处理 |
|---|---|---|
| Tool 语义不取决于保留 GoT | 采纳 | 最新用户已经解除 GoT 绑定；共享驾驶器可替换，请求/反馈边界不变 |
| association/fusion/trajectory head 是返回值处理基础 | 采纳 | 这是标准工程/学习基础，但必须把它完整实现，不能以“不算创新”为由继续保留弱接收器 |
| 必须按驾驶任务执行，真实结果影响后续请求 | 采纳 | `method_episode.prepare_request()` 绑定实际方案；P/F 的 `rank_targets()` 真正执行 current/change；是否有效仍需实验 |
| “取已有数据”和“调用能力”互斥 | 不采纳这个二分 | 参数化检索可以是能力；工具调用同样通过通信交付数据。是否存在独立贡献需要比较，不能由名词决定 |
| Tool 不能只是把现成缓存发回来 | 限定后采纳 | 不能忽略请求只返回固定包；但允许对合法缓存重新执行任务检索，也允许命中相同模型/上下文预测缓存，实际成本据实记录 |
| P 是按请求执行 perception/tracking | 当前不成立 | provider 使用已有因果跟踪状态；请求触发代理关系计算、排序、去重与装包，不重新调用检测器或跟踪器 |
| P 可以回答指定区域“有没有车” | 需要收紧 | 当前只能返回相关的已观测跟踪证据；`coverage='not_established'`，空返回不能证明区域无车或并线安全 |
| F 是 `conditioned_on=tau` / conditional motion forecasting | 必须改写 | tau 影响结果检索，不是 MTR 输入；当前没有预测其他车辆对 ego 方案的反应 |
| `P(B)` / `F(B, tau)` / 可变 horizon | 仅作概念例子 | 当前主方法请求是 current/change，预测返回时刻固定；没有任意 target_set/horizon 的调用接口，不能免费获得未知 peer ID |
| 把 Tool 替换成 message 后是否还成立 | 只能辅助检查叙事 | RPC 请求与返回本来就是消息；即便文字可替换，可执行任务与信息权限仍可存在。应用行为消融检验，不以词语替换作判定 |
| 只有融合有效、反馈无增量时应收缩叙事 | 采纳 | 不强保“反馈调用有效”的贡献；也不能因少量开发帧失败就下结论。应比较共同驾驶器和总预算下的强对照 |

[ReAct](https://arxiv.org/abs/2210.03629) 使用 Wikipedia API 获取已有知识，[Toolformer](https://arxiv.org/abs/2302.04761) 的工具包括搜索、问答和日历。它们支持“检索既有内容可以成为工具使用的一部分”；这**不证明本项目的 P 有创新，也不证明缓存策略天然公平**。合法来源、有效任务参数和实际成本仍须单独核对。

## 3. 建议采用的一页能力规格

### 总定义

**ToolV2X 研究驾驶任务条件下的远端能力调用：本车向持有私有因果观测的邻车发出可执行的 P/F 请求，根据真实返回修订驾驶方案，并据此决定下一次请求或 STOP。**

这里的“私有”表示尚未共享，不表示已经提供密码学隐私。“任务条件化”修饰请求的检索与执行语义；不默认意味着预测网络接受 ego 未来方案作为条件。

实际接口保留 `VehicleTools.query_task(request)`，不为更换名字增加新 API。

| 契约项 | P | F |
|---|---|---|
| 准确能力名称 | **任务条件化的因果跟踪状态检索** | **完整私有上下文上的运动预测与任务条件化结果检索** |
| 远端输入 | peer 截至 t 的源内跟踪状态、历史有效位、时间与 score | 同一完整合法 peer 跟踪上下文、冻结 MTR |
| 本车提供的任务参数 | current/change、实际新方案及必要的旧方案、时间坐标、ExecutionSpec、合法 receipt 引用 | 同左 |
| 提供方真实操作 | 根据 causal tracking-state motion proxy 计算时序相关性，排序；去除已回执字段，按预算返回原状态/历史 | 首次运行完整上下文 MTR，或在同一固定时刻/上下文命中缓存；随后按方案关系排序、去重、装包 |
| 返回内容 | anchor、原历史、valid/score/time、代理状态、来源与 receipt | anchor、六模式六时刻轨迹与分数、model_used、上下文及 receipt |
| tau 的作用 | 改变检索相关性及有限预算下选择的字段 | 改变预测结果的检索相关性与返回集合；不改变同上下文同目标的预测值 |
| 不具备的能力 | 请求触发新检测/重跟踪；可靠空闲区域证明；MTR 预测 | 对 ego 计划的条件反应预测；未声明可变 horizon；完整协方差输出 |
| 本地消费 | 状态/历史可直接经实体适配进入 driver；本地 MTR 作为显式选项 | 多模式未来直接经实体适配进入 driver |

current 使用新方案的时序相关性；change 使用旧/新方案在相同目标、模式和时刻上的有界相关性差异，再聚合。不是比较两个最终距离，也不是收到新 tau 就重新生成另一组 MTR 预测。

每次请求不必造成不同输出。例如两个方案涉及同样目标、预算足够覆盖全部目标时，合法返回集合可能相同。必须具备的是按固定规格执行、在构造出排序差异且预算受限时产生预期返回；不能强制生成不同结果来展示 Tool。

字段身份不包含 current/change 或请求编号。相同 source/scene/g/track/field/model/context 的原内容不会因为重新检索就成为新知识。provider 只承认自己发出的合法 receipt；receiver 派生等价另由 ledger 管理，不可伪造已购清单。

完整 P → receiver 同上下文 MTR 与 F 的对照保留。若未来引入真正 ego-plan 条件预测，必须同时改模型输入、预测上下文身份、缓存键、监督与等价控制；那是另一个有实质代价的能力扩展，本轮不采纳。

### 两端执行链

```text
本车因果输入 → 共享 driver D → tau0
  → 选择 P/F 与 current 请求
  → peer 真实执行 → 返回字段/receipt
  → Evidence Adapter：来源检查、实体关联、状态/预测编码与融合
  → 同一 D → 实际 tau1
  → 依据 tau0/tau1、已获信息和剩余预算选 current/change/STOP
  → 至多再调用一次 → 同一 D 得到最终方案
```

本地 adapter 不增加远端能力；它也不能免费读取 peer hidden features、目标表或未来标签。主方法、固定策略、强单轮和相同证据修订共用 adapter 与驾驶器。

## 5. 比换名字更有效的研究检验

| 问题 | 必要对照 | 支持的结论边界 |
|---|---|---|
| task 参数是否实际有用 | 相同 D/预算/能力下固定 ROI、current、current+old/union/change | 合同测试验证执行；独立数据才能说明任务效用 |
| 第一次返回后的驾驶反馈是否有用 | 同一真实首轮请求/返回/修订前缀，第二请求使用真实 tau1 或冻结 tau0 | 不能让两臂首轮证据、驾驶器或预算不同 |
| 是否只多计算了一次 | 固定 E/Z、同一 D 的有意义修订；匹配模型调用并记录耗时 | 确定模型重复完全相同输入只验证确定性，不是充分强对照 |
| 是否强单轮已经足够 | peer 内条件委托，可执行两个能力 primitive/STOP；与交替共用公平总预算 | 不把固定 PF 当强单轮，也不给交替臂额外免费模型计算 |
| 收益是否来自新融合器 | 新 D 下比较全部策略，另列旧 GoT 归档/兼容基线 | 不能以“新 ToolV2X 胜过旧 GoT”证明反馈机制 |
| F 是否只是换地方计算 | 完整 P 的相同来源上下文重算，固定实际入模信息 | 分开远端信息与计算委托价值，不保证 F 在每种预算下更优 |

并不要求每个场景、每种预算、每次第二调用都胜出。应报告质量—成本关系和哪些条件下 STOP 更合适；不能依赖结果筛选子集后宣称普遍收益。

工具检索和任务导向通信存在真实重叠。若最终只有融合器带来收益，就收缩或放弃“反馈能力调用优越”的论文主张；不能通过重新命名 P 或强制运行 detector 获得这个结论。

## 6. 对实施顺序的影响

1. **本轮先完成上述语义澄清。** 不重定义 wire、不增加新能力，不将 9-14-1 的例子当作新增 API 授权。
2. **随后继续完整驾驶端工作包。** 在同一现有 P/F 契约上完成实体适配、P-state/F 数值入口、共享驾驶器、交替/对照及数值监督。具体文件/API 沿用 [结构化规划器设计](structured_cooperative_planner_design_2026_09_14.md) 的依赖顺序。
3. **接口完成后才安排基础训练与机制比较。** 本轮不重训模型、不采集分支，不因语义争论继续扩大两帧联调。

现阶段不增加“请求触发高精度重检测/重跟踪”，不是因为它在原则上无价值，而是当前研究问题没有要求它，且需要新的传感器访问、能力实现及成本/监督设计。只有在具体失败模式说明该能力不可替代时，才作为独立扩展评估。

我对上一轮建议的调整是**把能力契约放在驾驶器选型之前说明，并且约束实现**，而不是撤销补齐协作驾驶基础的必要性。方法需要可执行的能力，也需要能可靠消费结果的共同驾驶器，两者是同一条链。
