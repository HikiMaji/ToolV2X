三、审查发现：哪些需要改，哪些只是尚未验证
发现一：无显式 control 的路径会漏记请求决策耗时
性质：代码层面的条件性缺口。应在正式质量—成本实验之前处理。
在 method_episode.py 中，请求预检、候选构造和策略决策实际都会执行，但控制耗时事件只有在以下条件成立时才写入：
if control_spec:
    # 写入 control 耗时
而评价器在没有 control_spec 时，不要求这些决策阶段存在计时记录，空记录集合会汇总为零。与此同时，正式运行规格的 control 经规范化后允许为 None。因此，确实存在一条合法路径：
策略做了计算，但该部分没有进入 total_compute_seconds，也没有被标记为未知。\

这里必须限定结论：
**不是所有实验臂都漏记。**使用显式 feedback 等 control 的路径已经记录这部分费用；也没有现成的方法效果结果因此被推翻。问题是默认/空 control 路径和显式对照之间，存在成本口径不一致的可能。
我的建议是做一个最小修复：**新版本中，请求预检与策略决策的计时不依赖是否指定 control；确实缺失的计时应显示为未知，而不是零。**若暂不修改计时实现，至少应在正式机制实验入口强制使用显式、已计时的 control，并拒绝混入未计时任务。
此外，现有 total_compute_seconds 本来就是若干测量阶段之和，代码明确排除了网络传输、部分执行器管理和归档 I/O，end_to_end_seconds 仍为空。不要把修复后的这个数也直接称作实车端到端时延。
发现二：必须区分“获得”“间接依赖”和“直接数值入模”
性质：关键测量口径，不是当前已证实的驾驶瓶颈。
新 receiver 有自己的容量限制。默认：
- 最多 64 个实体；
- 每个实体最多 4 组 forecast sets；
- 实体按当前与 ego 的距离等规则排序后截断。
这意味着即使 provider 根据 tau1 返回了不同证据，receiver 仍可能因为容量规则没有将它直接放进网络。**远端任务检索之后，还有一次本地容量选择。**是否实际触顶、是否丢掉重要证据，目前没有真实统计，不能先认定它已经造成了问题。
更容易误读的是 admitted_field_refs。
当前实现把参与关联、容量排序、自车识别和 prior 父依赖的字段，也计入这个集合。这个设计在来源追踪上是合理的，但它表示的是依赖闭包，不是“每个字段都作为直接 token 进入了网络”。
因此，下一阶段至少应该分开核对：
provider 实际返回了哪些新字段
             ↓
哪些字段直接进入 observation/forecast 张量
             ↓
哪些只参与关联、筛选或 prior 的间接依赖
             ↓
实际输入和最终输出发生了什么变化
直接入模的统计应依据 field_groups 的 use='tensor' 和 tensor_locations，而不是只数 admitted_field_refs。
**不建议现在盲目增加 64/4 上限。**先统计真实覆盖与截断，再决定是否需要调整；否则很容易再次把“增加信息量”与“改善反馈机制”混为一谈。
发现三：训练没有 target-as-prior 泄漏，但仍然是固定证据归档上的训练
性质：实现正确，但效果解释与数据组织需要明确。
这部分有一个重要的正确实现：training_loss() 会清空归档里的数值 prior，再用当前训练模型实际生成并 detach 的前一方案构造后续输入；GT 只参与轨迹损失。不是把真实未来轨迹喂回模型当先前方案。
但它重放的证据集合仍来自原始任务归档：
当前模型生成新的 prior
           +
当时采集并保存的固定证据集合
           ↓
监督下一次输出
训练过程中不会因为当前模型的 τ0/τ1 变化，就重新向 provider 检索证据。
**这不是数据泄漏，也不意味着训练方法错误。**它意味着：
这套训练先学习“在给定合法证据下如何输出与修订轨迹”，尚不能替代“当前模型如何引导真实查询”的交互评价。

尤其是新增初始化入口虽然解决了“没有检查点无法采集、没有采集无法训练”的启动依赖，却没有证明未训练模型产生的请求分布适合最终驾驶器。初始化权重能被加载，和能采到有代表性的 P/F 训练样本，是两件事。实现报告对此也没有声称已解决真实性能问题。
所以，下一步不能只看离线验证 loss，然后直接宣称真实交替链已经学好。应在基础驾驶器适配后，用冻结检查点重新执行有限、预声明的真实交互评价。
发现四：阶段权重已经被实现固定下来，但正式训练前应显式确认
性质：训练目标选择，不应误报成未披露的 bug。
目前导出每个阶段一行，但每行会再次监督它的全部前缀，并额外监督配置数量的最终同证据修订。于是早期阶段会重复出现在多个训练目标中。实现报告已经明确披露了这一点。
例如，仅考虑一个包含三个阶段的 episode，暂设 refinement_depth=0，三行分别优化：
\[
L_0,\qquad \frac{L_0+L_1}{2},\qquad
\frac{L_0+L_1+L_2}{3}.
\]若三行等权，三个阶段的累计系数比例就是：
\[
L_0:L_1:L_2=11:5:2.
\]这是根据当前循环和逐行平均方式得到的推导，不是实际训练结果。它说明训练目标并不是三个阶段简单等权；有额外 refinement 时，权重还会进一步变化。
这个选择可以保留，初始方案本来就重要。但应明确：究竟希望按 episode、阶段，还是训练行加权？不要到了结果不好时，再把未确认的阶段权重当成偶然实现细节。
另外，当前 fit() 在训练循环结束后才计算一次验证损失，没有提供训练过程中的周期验证曲线。正式长训练前，应增加周期验证，或用已有周期检查点执行独立验证；只保存检查点，并不等于已经具备验证监控。
发现五：强单轮接口已经接通，但不能把默认配置自动当成公平强对照
性质：实验配置风险，不是单轮接口没有实现。
当前 one-shot 提供 per_rpc 和 episode_aggregate 两类响应预算组织。默认 per_rpc 下，单轮外层响应上限可以只等于一次普通响应上限；而交替两次请求可能分别获得一次响应容量。
这可以作为一种“相同单次报文上限”的实验，但不能不加说明地用来证明：
在相同总资源下，两轮反馈优于强单轮。

要回答后一个问题，应利用已有的 episode_aggregate 等配置明确单轮总预算，同时计入请求、候选方案、summary、wrapper 和真实计算成本。
此外，目前单轮候选方案是预声明的 initial/slower/constant_motion 等有限类别。它是一个具体、可执行的条件委托对照，不是覆盖所有可能单轮程序的理论最优解。正式论文需要披露这个能力范围，而不是仅写一个“strong one-shot”名称。



五、我建议下一步按一个完整工作包推进
**不要继续每补一个接口就转去跑两帧误差表，也不要一次性把驾驶器与查询策略一起训练。**建议下一批围绕一个明确目标：
在当前 P/F 契约不变的前提下，建立并验收一个真正会消费远端证据的共享数值驾驶器。

阶段 A：完成少量必要修正，冻结真实运行规格
先处理成本计时缺口，补齐直接入模统计，明确阶段损失权重、周期验证方式和检查点选择规则。同步冻结数据录制组、预算、初始化种子、StructuredDriverSpec 与指标口径。
默认主训练建议使用同一 observations_only 规格下的 Ego、P-state、F、PF 证据条件。**P-local 先作为独立的同上下文等价与计算委托控制，不要无说明地混进默认 P-state 协议。**当前 p_processing 是完整 driver spec 的一部分，运行和训练都做严格匹配，并不是一个可随意切换、无需记录的临时开关。\
这一阶段不需要新 detector、新预测骨干、联合 RL 或重新绑定 GoT。
阶段 B：真实数据集成验收，然后训练共享驾驶器
第一批真实数据应来自预声明的训练录制组，并另设验证录制组；不要因为某些帧恰好让 F 有收益才选它们。
集成验收首先回答：真实历史是否完整到达输入、关联与自车识别是否合理、P/F 是否实际直接入模、未训练输出是否导致大量任务提前失败、训练与恢复是否能在目标环境运行。
通过后再开展完整的共享驾驶器适配，并持续记录阶段级验证表现。这里的重点不是“网络能不能把 loss 降下来”，而是：
它在不同证据条件下，是否学会了可解释且有任务收益的响应。

至少要有状态/本地信息参照、移除 P/F、错配证据和 prior 影响诊断。错配证据仅作为隔离的诊断条件，不得伪装成正常 provider 回执。
由于当前 prior 会直接作为残差基底，尤其要防止模型主要复制先前方案、忽略新增 P/F。这一风险应通过诊断验证，不应凭网络结构就认定已经发生。
阶段 C：用适配后的冻结驾驶器重做真实交互验证
基础训练结束后，先冻结同一个 D，用真实服务返回重新走一次有限交互链，而不是仅重放训练归档。
建议把每个任务的因果链拆成：
实际首轮返回
   → τ1 是否改变
   → 去重后下一动作/未购字段选择是否改变
   → 新字段是否直接入模，或通过哪条依赖起作用
   → 最终质量与实际成本是否改善
同时报告初始 STOP、首轮后 STOP 和两次调用的比例。
**不要求每个场景都多轮，也不要求每次修订都改变排序。**少数高价值场景的改善也可能值得额外交互，关键是完整数据上的净收益及其分布，而不是追求一个漂亮的“排序变化率”。
阶段 D：只有共同驾驶基础成立后，才拟合与比较查询机制
这时再进行当前项目真正要回答的三个问题：
问题	关键比较
实际修订反馈是否有增量？	相同真实首轮前缀后，使用 τ1 与冻结 τ0 的后续决策
是否只是多做了一次驾驶器修订？	固定证据的有意义 refinement，并匹配可用计算预算
为什么不能一次委托完成？	明确能力范围、同总预算的条件 one-shot


所有主机制对照共用同一驾驶器权重、adapter、输入规则和评价口径。不能用“新结构化 ToolV2X 胜过旧 GoT”来证明反馈机制。
也不必为了让调用次数整齐，强制所有任务用满两次远端调用或三次驾驶器前向。合理 STOP 节省的成本本来就是结果；额外计算对照应单独定义，而不是破坏主策略的停止行为。



所以从现在开始，我不会建议继续扩充 Method。最值钱的工作就是把 shared driver 训练好，然后尽快得到 feedback vs frozen-feedback vs strong one-shot 这三个决定论文命运的结果。
