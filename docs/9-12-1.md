**我需要纠正此前的两处说法。**

因此，合理的组合不是“BEAM 与 v0.1 二选一”，而是：

普通 MLP 就作为实现，不需要再给它一个新名字，也不需要人为构造一个输入、监督和结构完全一样的“普通 MLP 弱基线”。

## 三、真正可能形成论文核心的部分是什么？

我建议把核心问题收窄为：

> **在两端持有不同局部信息时，第一次实际返回引起的驾驶方案修订，能否帮助本车用有限的第二次请求，取得比普通计划检索或单轮委托更有用的 P/F 证据？**

对应执行链是：

\[
\tau_0
\rightarrow q_0
\rightarrow r_0
\rightarrow \tau_1
\rightarrow q_1(\tau_0,\tau_1)
\rightarrow r_1
\rightarrow \tau_2
\]

其中每条 \(\tau\) 都是同一个驾驶器的真实输出，每份 \(r\) 都是实际远端执行结果。

### 为什么这条思路有合理性？

设本车私有输入为 \(X_E\)，首轮发出的任务摘要为 \(m_0\)。收到邻车结果 \(r_0\) 后，本车产生：

\[
\tau_1=D_\phi(X_E,r_0).
\]

下一次需求可能依赖 **\(X_E\) 与 \(r_0\) 的联合结果**。邻车只有初始摘要和自己的输入，不一定知道本车最终会如何修订方案。这就给实际反馈留下了价值空间：把“收到这份信息后，本车现在真正需要什么”传回提供方。

**但这不是两轮必胜的证明。**如果一个便宜的初始摘要、几个候选方案，或者一个条件执行程序，就足以让邻车完成相同选择，单轮可能更好。

这恰恰是你稿件中“允许 peer 条件执行的单轮委托”特别重要的原因。应把它作为核心反方对照，而不是可有可无的消融。

### 与 ToolV2X 主线是否一致？

**一致，而且比“根据场景选 P/F 标签”更贴合。**请求定义任务，提供方使用尚未共享的输入执行，返回改变本车驾驶与后续请求；这些构成了实际能力委托。

你对“本车不能等价完成”的修订也正确：不能免费得到邻车私有输入，不等于付费取得完整 P 后仍然不能重算 F。需要注意，“私有输入”在这里表示**信息尚未共享**，不是已经提供密码学或差分隐私保证。

目前公开 `episode.py` 的确没有在工具循环中生成驾驶修订，所以这不是“继续训练现有五策略驾驶器”就能自动获得的功能，需要新的交替执行路径。

## 四、v0.1 有六处应该在实现前进一步明确

### 1. `change` 必须是有界、时间对齐的关系变化，不宜直接用距离变化量

你强调时间关系是对的，但目前还缺一个冻结后的执行定义。

直接按照

\[
|d_{\rm new}-d_{\rm old}|
\]

排序会有问题：远处目标从 100 米变成 80 米，数值变化比近处目标从 2 米变成 4 米更大，但并不意味着前者更值得请求。

一个可实现的首版是先定义有界相关性。令 \(d_i^m(h;\tau)\) 表示在时刻 \(h\)、目标模式 \(m\) 下，与 ego 方案的、考虑车辆尺度的非负间距代理：

\[
\rho_i^m(h;\tau)
=
\exp\!\left[-\frac{d_i^m(h;\tau)^2}{2\sigma^2}\right].
\]

然后固定：

\[
S_{\rm current}(i)
=
\max_{h,m}\rho_i^m(h;\tau_{\rm new}),
\]

\[
S_{\rm change}(i)
=
\max_{h,m}
\left|
\rho_i^m(h;\tau_{\rm new})
-
\rho_i^m(h;\tau_{\rm old})
\right|.
\]

重点不是这个核函数有什么创新，而是**先在同一时间、同一模式上比较，再聚合**。

例如相关性从 \((1,0)\) 变成 \((0,1)\)，两条方案的最大相关性都是 1；若先求最大值再相减，会错误地得到“没有变化”。逐时刻比较则能保留相遇时刻变化。

P 使用合法历史趋势作为检索代理，F 使用 MTR 模态；这里的相关性不是校准碰撞概率。**同一份他车预测分别与两条 ego 方案比较，也不意味着预测了他车对 ego 改道的反应。**

这组定义、平局规则、尺度和缺历史处理应先固定，再做效果实验。

### 2. 第二次应该请求“尚未取得的字段”，而不是反复返回同一份内容

这是你稿件还可以补强的地方。

在固定 \(t\) 内，current 和 change 可能反复选中同一个目标。若第二次返回的还是相同 P 历史，或相同上下文生成的 F，**请求名称变化了，信息并没有增加**。

建议请求增加一个只包含已知内容的 **acquired-field manifest**，描述已经取得的：

\[
(\text{提供方、时间、目标句柄、字段、模型/上下文版本}).
\]

这些清单也计通信成本。提供方据此区别：

- 同目标、同历史：已知内容，可以引用或跳过。
- 同目标、局部预测与完整上下文预测：可能不同，不能无条件跳过。
- 已有 F、再补原始历史：可能有增量。
- 新目标：正常返回。

**不能简单按 track ID 去重整个目标。**需要按字段和计算上下文识别重复。

这可以防止最后得到的所谓 `change` 收益，实际只是同一信息被重新展示、重新排序或重复强调。后一种效果可以研究，但应该归为表示或推理效果，而不是新增证据价值。

### 3. 将已购信息 \(E_k\) 与驾驶器实际输入 \(Z_k\) 分开，作为正式状态

你稿件已经意识到这个问题，我建议把它提升为方法公式，而不只是日志要求：

\[
E_k=E_{k-1}\cup r_k,\qquad
Z_k=S(E_k,\mathcal B_{\rm ctx}),\qquad
\tau_k=D_\phi(X_E,Z_k).
\]

这里 \(E_k\) 可以不断积累，但 \(Z_k\) 因截断可能不是单调增加的。

因此，第二次查询的实际收益可能同时包含“获得新目标”和“挤掉旧目标”。价值网络应该知道入模变化与丢弃内容，收益标签必须来自实际 \(Z_k\) 产生的轨迹。

同时，**新接收表示必须供所有方法共用**。不能给新机制任务优先排序，却让固定或计划检索基线继续用旧的距离排序，再把差异算成查询机制收益。

### 4. 明确驾驶修订无效或不稳定时怎么办

`change` 依赖驾驶器，所以方案变化可能来自有效新证据，也可能来自生成噪声、格式错误、截断或不合理的轨迹摆动。

需要预先定义：初始方案无效时是终止并计失败，还是使用带来源标记的公共回退参考；相同证据、相同解码条件下输出应如何核对；明显异常的修订是否允许继续形成任务。

**不能仅保留初始方案可解析的样本来展示机制收益，也不能把回退轨迹称为 GoT 的修订。**

此外，若错误初始方案把所有请求都限定在错误方向，current/change 可能都看不到真正相关区域。应保留宽覆盖对照，必要时设置所有方法共享的覆盖规则，而不是只给新方法额外全景信息。

这不要求底座先达到最优，但要求它具备最低限度的稳定性和证据响应能力，否则很难解释反馈实验。

### 5. 两步监督方向正确，但应写清完整净收益及教师版本

最后一次调用的目标可以写成：

\[
Y_1(s,a)
=
L(\tau_s,y)-L(\tau_{s'},y)-c(s,a),
\]

STOP 为 0。

首步剩两次调用时，用未在当前录制组上训练的冻结续策略 \(\hat\pi_1^{-g}\)：

\[
Y_2(s_0,a)
=
L(\tau_0,y)
-
L\!\left(\tau_{\rm end}^{a,\hat\pi_1^{-g}},y\right)
-
c_0
-
\mathbf1_{\rm continue}c_1.
\]

这样第一步即使即时收益为负，也可能因为提供了后续定位线索而有正的终态价值。

你禁止“每帧先看 GT 选最优第二动作，再称为可部署回报”，是合理的。但表述应精确：**离线用 GT 制作标签本身不是泄漏；问题是先知续动作会造成过于乐观的可达价值。**

另外，若最后部署的是一个共享网络，继续训练首步可能改变其末步行为。应保留末步监督、固定续策略版本，最终实际 rollout。不能网络已经变化，却继续拿旧教师产生的标签均值当部署性能。

交叉拟合按物理录制组进行，包含两车来源、相邻帧及全部分支。它仍不能自动消除“驾驶器在自己的训练场景上误差过低”的影响，可另设机制校准子集检查，不必立即训练多套 7B。

### 6. 硬预算必须使用请求前合法可知的量

你正确要求按真实成本制作标签，但在线决策时尚不知道精确响应大小、未查询提供方的完整目标数和实际执行时间。

因此要区分：

**离线收益标签**可以使用实际成本；**在线可行性判断**只能使用公开输出上限、合法缓存状态、历史估计或期望成本，不能先运行未购买服务再决定买不买。

固定返回目标数不等于固定字节，更不等于固定 token。P/F 的历史、字段、模式、头部长度不同，应明确完整报文预算和超额行为。

训练效用可以采用预定尺度归一化和权重，但结果不能只报一个混合分数；原始双向字节、提供方计算、接收计算和 GoT 时间要分别报告。尤其不能把 **三次 GoT 对一次 GoT** 的代价省略。

## 五、怎样验证它不是“普通轨迹筛选器＋多算两次”？

我认为最关键的是下面这组实验，不是先增加更复杂的网络。

| 对照 | 固定什么、改变什么 | 要回答的问题 |
|---|---|---|
| **标准价值选择器：固定 ROI vs current 任务请求** | 相同状态信息、价值训练与能力模型，改变请求语义 | 任务级请求本身是否有用？ |
| **current＋change vs current＋old / 时空并集** | 相同 P/F 候选数、监督机会和预算 | 旧新关系差分是否优于普通计划检索？ |
| **真实修订反馈 vs 冻结初始方案** | 固定同一首轮请求与实际返回，改变第二请求所用的方案 | 是驾驶修订在起作用吗？ |
| **两轮交替 vs 强单轮条件委托** | 允许单轮使用合法 ego 摘要、候选方案、条件计算和预算内 bundle | 第二轮真的不可被便宜的一轮替代吗？ |
| **新增证据再规划 vs 同证据额外生成/迭代** | 匹配驾驶计算量 | 收益来自信息还是多算了一次？ |
| **同目标 P/F 终态诊断** | 相同目标、背景与容量，分别替换预测上下文和历史字段 | P/F 的差异究竟来自哪里？ |

还应保留本车块固定和 **Ego-max-context** 两类参照，避免工具胜出只是因为无通信基线白白预留了远端容量。

这里尤其需要注意两个归因问题。

**“相同数量的动作”只是必要控制，不是充分控制。**对照请求也必须有合理的表达能力，不能给 change 四个精心设计的候选，再给对照四个无关区域。

**“普通 MLP”不是需要击败的敌人。**如果它接收相同状态、执行相同请求并使用相同监督，它就是你的算法实现。要验证的是任务请求和反馈设计，而不是给同一个网络换名称后比较。

## 六、接下来应该怎样推进，而不是再写一轮大框架？

我建议分三步，**现在没有必要恢复大规模训练或增加联合 RL**。

**第一步：把 v0.1 补成冻结的执行规格。**落实 current/change 的时序关系、已知字段清单、预算与失败规则、E/Z 接收账本，以及真实 GoT 的交替调用。先只增加一个请求价值模块，provider 排序保持确定性。

**第二步：在事先确定、覆盖录制组的小集合上，完整展开合法分支。**按你的动作集，在无失败、不复用输出的情况下，每帧最多需要：

\[
1\ \text{个初始方案}
+2\ \text{个首轮 P/F 后方案}
+2\times4\ \text{个次轮请求后方案}
=\mathbf{11\ 个驾驶输出}.
\]

STOP 直接复用当前方案。这是该有限动作树的推导，不包含额外基线或多次随机生成。

先检查：反馈是否改变请求；是否获得不同的、尚未购买的字段；这些字段是否进入驾驶器；同证据额外计算能否解释变化。**原五条件记录不够做这些检查，需要新分支，但无需每条分支都重训模型。**

**第三步：才进行记录级交叉拟合的价值学习和真实 rollout。**底座、接收器与请求程序在制作对应标签和比较期间冻结。先完成上述强对照，再决定是否扩大数据、增加驾驶适配或更换价值结构。

这里的小规模完整分支实验不是用一个弱模型决定项目生死，而是尽早发现：你设计的请求程序到底有没有产生声称的信息变化。

## 七、最终判断：主线可以守，但应该守研究问题，不应硬保 `change`

我会把当前候选评价为：

**工程可实现性较明确，逻辑比 BEAM 完整；有可辨识的研究假设，但还没有足以保证论文核心成立的新颖性与实验依据。**

- `change` 不优于等规模 current/old/并集：删除差分请求贡献，保留任务条件化请求。

- 学习器不超过强规则：检查效用可预测性、监督和估计误差，不自动扩大网络。
- 整套方案在公平预算下仍不超过普通共享与强计划请求：**当前论文机制证据不足，需要重新设计，而不是只换成 Tool 的名字。**

> **ToolV2X: Task-Conditioned Cooperative Queries with Replanning Feedback**
> 任务条件化协作请求与驾驶重规划反馈。

真正值得证明的不是“车会调用工具”，而是：

> **真实驾驶修订反馈在双方信息未完全共享、总预算受限时，能够组织比强单轮委托和普通计划检索更有效的能力请求。**
